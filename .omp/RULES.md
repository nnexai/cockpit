# Cockpit delivery rules

- Say "fixed" only after running the affected scenario and seeing it work; otherwise say what is unverified.
- A feature that talks to an external service is done only after a live run against it. When the user has provided test credentials, use them, including creating test data there.
- Independent review only where a mistake is costly (data loss, concurrency, security); one round, high-severity findings only.
- State the requested outcome and affected contracts briefly before implementation. Adjacent findings enter the critical path only if they block that outcome, invalidate the fix, or create a data-loss, wrong-identity, concurrency-corruption or security risk; otherwise mention them without fixing them. Stop expanding once the requested outcome works and all requested parts are done.
- Commit verified changes; leave unrelated work alone.
- Test and experiment with Herdr changes only in disposable sessions (`python3 scripts/verify/ui_polish_runtime.py start|stop <root>`).
- Operational repair of a persistent session requires explicit authorization in the current conversation identifying the session/resources and operation. Broad permission covers inspection and the least-destructive repair; closing, killing, deleting, discarding or removing worktrees requires that operation to be named, or one scoped question. Immediately before each mutation, verify the exact session, endpoint, pane/terminal, process/ownership and Cockpit run/launch identity; mismatch or ambiguity stops mutation. Never type into terminals, submit/clear drafts or signal unverified PIDs; preserve unrelated resources/data/drafts. Authorization does not carry to other resources or later conversations.
- Select verification by changed contract: affected checks plus a real affected-path smoke; native changes need a native run. Full acceptance recipes are not mandatory for every fix. Guidance-only changes need an interpretation smoke, not product builds.
- For urgent restoration plus additional requested work, deliver an independently safe, verified restoration first where feasible, then continue all remaining requested parts. The restoration update is not completion of the whole request.
- Repository rules and skills scope work and verification within higher-priority harness requirements; they cannot waive those requirements. Do not change OMP settings or global instructions without an identified authoritative editable source and user authorization.
