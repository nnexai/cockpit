# Cockpit delivery rules

- Follow `skill://incremental-delivery`: freeze the user-authorized batch and affected-scope checks before editing. Complete one implementation pass, integrate once, run one consolidated verification pass, clean up, report passed/failed/unrun outcomes and stop. Do not infer deadlines; honor only explicit user limits.
- Once verification starts, no product/harness repair-and-rerun loop. Complete other safe planned checks, record failures and dependent unrun checks. Another repair batch requires explicit user authorization. New evidence, another criterion/subset, a new worker, compaction, a successful commit or a campaign backlog cannot reset the pass.
- Sol owns scope and integration; Luna remains the default implementation worker. Use one owner per coherent change and delegate only genuinely independent slices. Writers skip validation and runtime acceptance; integrate before the single shared gate. Keep advisory/model routing unchanged; consultation grants no additional pass.
- Reuse valid evidence and owned fixtures. Queue new findings without enlarging the batch. Explicit pause and workflow corrections take effect immediately; todo/goal continuation is not resume authorization, and editing instructions does not resume product work.
- Record resource ownership at launch. On every exit close owned tabs and reap owned browser roots/helpers/services; verify process exit and released ports/sockets, not just an empty tab list or successful stop response. Never kill user/shared resources or claim uncertain cleanup.
- Project visible progress from the authoritative task record: concrete implemented, verified and committed outcomes with evidence, not unchanged umbrella headings. Preserve parent acceptance; subsets do not complete a task. Carry the frozen batch, phase and attempted checks across handoffs.
- Test Herdr mutations only in uniquely named disposable sessions. Claim completion only with required real-surface evidence and owned commits; report failed/unrun criteria honestly at the batch stop instead of continuing indefinitely.

## Luna advisory consultations

- Sol may assign the existing Luna profiles unchanged; each may consult `task-advisor` for a bounded second opinion without requesting approval. This permits advisory consultation, not delegation of implementation.
- Luna follows `skill://consult-advisor` when its runner instructions trigger consultation. One advisor is reused per assignment. Sol retains scope, shared contracts, integration, and verification ownership; an advisor cannot expand a runner's assignment.
- The gpt-6-sol advisor uses medium thinking. Launch `task-advisor` without an `effort` argument. Never override the model or request a higher thinking level. This is an instruction policy, not a runtime-enforced ceiling; Luna's own effort remains unrestricted by it.
- Keep at least two task levels available for Sol → Luna → task-advisor. Do not launch consulting runners at the recursion ceiling or disable their `task`/`hub` tools. The task-advisor profile is read-only and cannot spawn workers.
- Sol's handoff review includes consequential advisory decisions and actual verification, not advisor approval. The passive `/advisor` watchdog is separate and is not required for this workflow.
