# Bootstrap coverage matrix

This report is an independent review aid for `BOOTSTRAP_PLAN.md`. It traces the confirmed architecture that repository bootstrap work can affect. It does not authorize implementation beyond the current foundation. The bootstrap must produce working behavior, not empty crates or files that merely reserve names.

This matrix records bootstrap-era constraints. Its protocol-20 terminal rows are superseded by `DECISIONS.md` and the protocol-22 generation-1 client-shell implementation.

## Cross-cutting traps to flag in review

- **Shallow modules:** a package or adapter that only re-exports types, forwards raw JSON, or contains no real foundation behavior is a placeholder, not a seam. Every package named in the plan needs a concrete owner and an exercised path, or the plan must defer the package rather than create it.
- **Duplicate hosts:** there should be one `cockpit` executable and one `cockpit serve` gateway. Tauri is the native host. The browser is the same frontend behind the gateway, not another native host or a second server.
- **Placeholder packages:** do not add `cockpit-providers` merely to make a six-package diagram true. The provider boundary may be deferred until a concrete provider exists. The same rule applies to any package with no immediate behavior.
- **Duplicated TypeScript protocol:** TypeScript must consume generated or otherwise derived bindings from the Rust protocol source. A hand-written parallel DTO/error/event schema is architectural drift even if names currently match.
- **Unsupported verification claims:** the current workstation has Herdr 0.8.2 and Rust/Bun/tooling, but lacks the Fedora WebKitGTK/GTK native development stack and has no global `cargo-tauri`. A plan may verify browser, Rust, fixture, and loopback behavior now. It must leave the exact Tauri compile and native launch smoke explicitly blocked until approved Fedora provisioning.
- **Authority leaks:** Cockpit caches and presents Herdr state. It must not invent PTY, process, session, workspace, focus, layout, or inbox authority.

## Reviewer checklist for `BOOTSTRAP_PLAN.md`

### Scope and tree

- [ ] Does the plan name exact files and owners for every now item?
- [ ] Does it keep one Rust workspace, one `cockpit` binary, and one frontend package?
- [ ] Does it omit provider packages until a concrete provider implementation starts?
- [ ] Does every planned package contain immediate real behavior rather than a placeholder `lib.rs`?
- [ ] Does the dependency graph enforce protocol → core → adapters/hosts, with no host transport in core?

### Protocol and Herdr

- [ ] Is the protocol versioned, sourced in Rust, and free of a hand-maintained duplicate TypeScript schema?
- [ ] Does the plan target Herdr 0.8.2/protocol 20/schema 1 through schema and capability gating?
- [ ] Are endpoint and named-session selection configurable, with no hard-coded observed socket path?
- [ ] Do snapshot, subscribe, ordered events, request IDs, structured errors, reconnect, and resync have named files and owners?
- [ ] Are unsupported capabilities and takeover conflicts explicit states rather than silent fallbacks?
- [ ] Does session switching detach old streams and reject late old-session events?

### Hosts, frontend, and security

- [ ] Is `CockpitClient` the only contract used by UI components?
- [ ] Do native and browser adapters map equivalent semantics without leaking transport details?
- [ ] Does `cockpit serve` run in the foreground, bind loopback, serve the same static artifact and API origin, and support deterministic test mode?
- [ ] Does Tauri use explicit capabilities, named-window targeting, and a narrow command allowlist?
- [ ] Are raw shell, raw socket forwarding, broad filesystem/process/network permissions, and remote access absent?

### Terminal and UI behavior

- [ ] Is Herdr the PTY/process/scrollback/ownership authority, with xterm.js limited to rendering and input hooks?
- [ ] Are renderers and live streams limited to visible panes in the selected tab, with idempotent disposal and remount resync?
- [ ] Do focus/layout actions go to Herdr and reconcile from authoritative responses/events?
- [ ] Does magic escape precede xterm input and GUI shortcuts without hard-coded undocumented bindings?
- [ ] Do attach and operation failures retain visible last-known state with inline retry/resync actions?

### Toolchain and proof

- [ ] Does Bun own frontend installation and scripts with one checked-in lockfile and frozen installation?
- [ ] Does the plan avoid global installs, Corepack integrity bypasses, and Fedora-inappropriate Debian commands?
- [ ] Does it state the Rust, Bun, Node, Herdr, and native-package prerequisites without claiming unavailable packages are installed?
- [ ] Are verification commands separated into runnable-now checks and blocked native smoke?
- [ ] Does each verification claim name the behavior exercised, rather than only checking file existence or compilation?
- [ ] Are contract fixtures safe, deterministic, and free of real user terminal bytes or secrets?

A plan that fails any authority, duplicate-host, placeholder-package, protocol-source, or native-verification item is not ready to serve as bootstrap authority.
