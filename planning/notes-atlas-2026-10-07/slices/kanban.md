### Interaction/state details

- **Source order and no rank invariant.** Every lane filters the existing todo sequence; it does not sort by a generated rank. The insertion marker is rendered before the first target-lane member whose source line exceeds the dragged task line; ghost/status explicitly says “file order” (`Kanban.tsx:170-191`). `kanbanDropOperation` returns only `kanban_move` with captured selector and destination—no position/rank (`boardState.ts:9-16`). Core `KanbanList` iterates parsed items and pushes into lanes in that order (`crates/cockpit-core/src/notes/todos.rs:68-92`).
- **Checkbox/open-lane invariant.** Done lane is derived for checked tasks, even if their persisted lane remains Backlog or Doing (`Kanban.tsx:14,170-191`). Dragging to Done announces it checks the task; dragging an already-checked task to Backlog/Doing announces it reopens; landing on current effective lane is no-op (`Kanban.tsx:125-129,161-169`; `boardState.ts:13-15`). Core move to Done changes checkbox while retaining prior lane metadata; Backlog/Doing unchecks and sets lane (`todos.rs:755-773`). Normal checkbox action only toggles checkbox (`Kanban.tsx:60`).
- **Empty/loading/error variants.** Zero board members shows board empty prompt/action; each empty lane displays a list item “No cards.” with count zero (`Kanban.tsx:170-185`). `Kanban` itself has no explicit loading placeholder: data/polling lifecycle belongs to `useNotes` / Notes view, and mounted panel renders from model data (`NotesView.tsx:137-151`; `useNotes.ts:65-160`). No board-specific lane read error appears in the inspected component; shared Notes-level error slot handles model errors (`NotesView.tsx:153-155`). Comment-specific loading, empty, error/retry states are in N-KAN-05.
- **Disabled/pending/error.** Card mutation/drag is disabled for `model.busy`, `notes_outcome_unknown`, malformed metadata, or lazy continuation; detail move/unboard/promote is disabled for busy/unknown (`Kanban.tsx:26-28`; `TaskDetail.tsx:182-185`). The add submit disables for busy, empty draft, unknown outcome (`Kanban.tsx:133`). Mutations that cannot be confirmed are not retried automatically; code announces that saved location was refreshed and asks users through shared error slot to check before the next write (`Kanban.tsx:169`; `NotesView.tsx:153-155`).
- **Conflict and recovery.** Stale drag snapshot is canceled rather than silently rebased; saved-title conflict preserves draft and gives Keep mine/Reload (`boardState.ts:9-16`; `TodoTitle.tsx:62-74`). Details panel reports deleted task while retaining its comments/drafts (`TaskDetail.tsx:186,212`).
- **Focus/DOM semantics.** Cards are list items, lane wrappers are div dropzones carrying `data-col`; lane jump controls form a labeled group, and lane add buttons focus shared input. Drag handle's accessible name includes task text. Keyboard cancellation attempts to preserve expected tab order, and accepted/canceled moves restore focus to the card handle only if browser focus is still on body/the same handle; it avoids taking focus from a dialog/inert surface (`Kanban.tsx:49-60,85-114`). NotesView detail-close restoration checks connected opener and current focus ownership (`NotesView.tsx:102-111`); it has no explicit modal-dialog check in that callback. CSS makes handles and comment buttons transparent until hover/focus-within (comment also visible with counts/drafts/selection); focus-within reveals keyboard-focused controls (`notes.css:128-143`).

### Evidence-backed UX observations (not design proposals)

1. The lane-add control is named “Add a card from {lane}” to assistive tech, but all three focus the same input labeled “Add a card to Backlog”; its title likewise always says “Add a card to Backlog” (`Kanban.tsx:133,170-191`). This appears potentially inconsistent in user-facing intent; no lane-specific insertion occurs in that handler.
2. The board’s whole-card whitespace opens details, but keyboard users reach detail through the separate comments button; the card itself is not a button and no `role`/tab stop is assigned (`Kanban.tsx:44-48,61`). This is a code-derived interaction asymmetry, not proof of runtime accessibility impact.
3. The handle and comment opener are opacity-hidden absent hover/focus (except comment count/draft conditions); keyboard focus makes them visible, while touch-only visibility depends on browser hover behavior not established by source inspection (`notes.css:128-143`).
4. Empty lanes display “No cards.” and a header add button; all header add buttons focus the shared Backlog composer rather than directly creating in that lane (`Kanban.tsx:170-185`). The entirely empty board also has a larger message/action.
