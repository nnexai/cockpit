## Surface atlas

### N-REC-01 — Shared draft data and browser persistence
**Sources:** `src/app/notes/drafts.ts:1-23` (`TextDraft`, `DecisionDraft`, `NotesDrafts`, `emptyDrafts`, `reconcileDraft`, `changedDraft`, `acknowledgeDraft`); `drafts.ts:24-74` (`key`, `memory`, `listeners`, `subscribeDrafts`, validation, `readDrafts`, `storeDrafts`, write-failure warning).

- Draft records include scratchpad, todos, decision edits/new decision, comment edits/new composer, add-todo/add-card text, plus `unknownOutcome`. Each `TextDraft` carries `value`, prior saved `base`, `revision`, and `conflict`.
- Key is `cockpit.notes.drafts.v1:${notesId}`. Memory and listeners are keyed by the same Notes UUID. Writes update memory and synchronously notify same-process subscribers before attempting `localStorage.setItem`.
- Reads memoize parsed records in memory; text drafts/dictionaries are filtered by shape. Missing, malformed JSON, invalid top-level value, or storage-read failure returns empty drafts. Invalid individual dictionary entries are filtered. In the catch path read returns empty drafts and does not set a visible storage warning.
- Write storage failure returns visible warning text: draft retained only for this app session, save before restarting Cockpit. Storage is not an authoritative durable copy; localStorage persistence is best-effort.
- `reconcileDraft`: clean/no draft adopts server content+revision; dirty draft keeps its value/base/revision and raises conflict if revision differs, preserving an already-raised conflict. `acknowledgeDraft` advances base/revision after confirmed save and preserves typing done after the submitted snapshot.

**Conservative invariants:** never treat cached draft content as server-confirmed; only confirmed write response advances draft base; server revision changes do not overwrite dirty local value; explicit reload may discard only the selected draft. Storage failure means process-session retention only, not durable recovery.

### N-REC-02 — Shared loading, refresh, pending writes and errors
**Sources:** `src/app/notes/useNotes.ts:6-42` (`pendingWrites`, listeners, `NotesModel`, `notesError`, `notesMutationError`, todo identity/selector); `useNotes.ts:43-97` (state, subscription, refresh); `useNotes.ts:98-137` (mutation); `useNotes.ts:138-169` (polling/cleanup/error acknowledgement).

- One write at a time per Notes UUID via module-level `pendingWrites`; listeners synchronize busy indicators across mounted views of that same ID. `mutate` returns false if pending or outcome-unknown.
- Refresh reads scratchpad, all todos, and all decisions concurrently; epoch and alive guards discard stale/unmounted results. Unexpected result kinds throw. Successful refresh installs server documents then reconciles scratchpad/todo/decision-edit drafts. For decisions, any summary revision difference marks both title and body edits conflicting. Refresh does not reconcile comment drafts (comment consumers own that read path).
- Initial refresh runs on mount. A 3-second timer and focus/visibility events resolve target tokens; changed tokens or forced poll trigger content refresh. Polling suppresses concurrent poll requests and ignores errors while write outcome remains unknown.
- A recognized authoritative `notes_*` operation error stays authoritative. A transport/unclassified error is converted to `notes_outcome_unknown`; it persists `unknownOutcome`, blocks writes, and attempts refresh without replacing the actionable error. A successful write invokes captured success handler, special-cases todo draft-key migration, then refreshes; refresh failure reports “Change saved, but refresh failed…”. Busy clears in `finally`.
- Acknowledging by `setError(null)` also removes persisted `unknownOutcome` and clears the guard. The UI only calls this for unknown outcome after explicit successful saved-state read and user acknowledgment.

**Unknown outcome and recovery states:** pending = busy and other writes refused/disabled; known conflict = error code `notes_conflict`, separate from uncertainty; unconfirmed transport outcome = persistent guard and warning, no automatic replay; read-check failure retains uncertainty/no proof; successful read produces review prompt but still blocks writes until explicit “I checked saved state; allow next write”; a later uncertain write revokes that proof. See behavioral test references N-REC-07 and the test map below.

### N-REC-03 — Scratchpad editing/conflict/recovery
**Sources:** `src/app/notes/NotesView.tsx:113-124` (`saveScratchpad`); `NotesView.tsx:136-141` (tab panels and scratchpad/Todos UI); `NotesView.tsx:150-161` (global problem and storage alerts); `drafts.ts:15-23` (revision operations).

- Scratchpad draft edits are kept in `model.drafts.scratchpad`; editor save submits captured content with draft revision. “Keep mine” submits against current scratchpad revision, while normal save is suppressed when conflict exists. Confirmed response reconciles against server-normalized content and preserves newer typing.
- Dirty state text distinguishes saving, saved, and draft-kept. Conflict shows current saved Markdown disclosure and reload/keep-mine controls (rendered on same scratchpad block; source in `NotesView.tsx:138`, line contains the full JSX). Save is gated on loaded scratchpad, changed draft, no pending write/unknown outcome, and no unresolved conflict unless keep-mine chosen.
- Scratchpad panel renders the editor when its draft is available; otherwise it explicitly renders “Loading scratchpad…” (`NotesView.tsx:138`). Global errors are shown in a problem slot with role alert and code; storage warning is separate role alert.

**Invariant:** expected revision is the draft's original token unless explicit Keep mine uses current server document revision. Do not infer that text appearing in editor is saved.

### N-REC-04 — Todo identity, draft conflicts, source capture and retained source drafts
**Sources:** `src/app/notes/useNotes.ts:28-42` (`todoIdentity`, `todoSelector`); `useNotes.ts:82-96` (refresh reconciliation); `src/app/notes/TodoTitle.tsx:14-21,42-73` (draft identity and update); `src/app/notes/RetainedDrafts.tsx:4-32` (orphan drafts); `src/app/notes/NotesView.tsx:141-144` (todos and source path); `crates/cockpit-protocol/src/notes.rs:60-75` (Id selector with expected revision vs Ref selector).

- Unique non-duplicate ID is stable key and mutation selector includes expected item revision. Missing ID or duplicate-ID task uses file reference (`L<line>@<file revision>`) instead; duplicate IDs must not alias drafts. Backend reference has file-revision freshness semantics (protocol selector at `notes.rs:60-75`; core rejection references in `todos.rs:571-590`).
- Todo edit save refuses a dirty conflicted draft unless explicit Keep mine, and submits selected task identity captured by current todo; explicit Keep mine uses current identity/revision. Reload discards edit by resetting to current saved title/revision. Successful save migrates draft key to returned identity and preserves typing entered during request (`TodoTitle.tsx:42-56`).
- Refresh only reconciles drafts for tasks still present. RetainedDrafts then lists dirty todo drafts whose key no longer exists and dirty decision edits whose ID no longer exists. It offers read-only selectable text (click selects) and per-item discard; no target is guessed and no automatic migration occurs. Component is hidden until `model.scratchpad` is truthy (`RetainedDrafts.tsx:5-12`), so unavailable scratchpad suppresses this recovery display as written.
- Todos source affordance exposes `${info.folder}/todos.md`, read-only/click-select, explaining board and Todos share ordinary file and preserve headings/prose/task boundaries (`NotesView.tsx:142`).

**Conservative invariant:** stable record IDs plus revisions qualify mutations; line refs are document-revision-qualified. Never retarget a missing/ambiguous source draft automatically.

### N-REC-05 — Comment source capture, refresh and orphan recovery
**Sources:** `src/app/notes/TaskDetail.tsx:28-78` (composer, thread identity/read/poll/reconcile); `TaskDetail.tsx:98-164` (post/save/repost/orphan selection); `TaskDetail.tsx:165-194` (keyboard/focus/loading/error/empty); `TaskDetail.tsx:195-224` (comment edit/conflict/deleted-state UI and composer); `NotesView.tsx:91-101,127-128,143-145,151,159-161` (adoption/selection/detail mounting); `crates/cockpit-protocol/src/notes.rs:166-175` (comment ID and expected revision operations).

- Detail is mounted with `key={surface.selectedTodo}`, receives `todoId` captured from selected todo ID, and uses it for comment requests and draft keys `${todoId}/${comment_id}` or composer key `todoId`. `openDetails` remembers opener; a task without unique ID/duplicate ID first issues explicit `todo_update` by file ref to adopt it and opens only when response returns an ID (`NotesView.tsx:92-103` within inspected NotesView range 29-126). This distinguishes stable todo identity from mutable line references for comments.
- Comment list reads immediately, every 3 seconds and on focus; each visible comment reconciles draft by revision. Loading suppresses count; read errors show inline Retry reading; empty state distinguishes task existing vs removed. Scroll restores per `${notesId}/${todoId}` in-memory position; additions below current viewport accumulate “new comments below”.
- Add-comment composer draft (body/author) persists under captured todo ID. Successful response clears body only if its current body equals submitted snapshot; newer typing stays. Add is disabled for missing todo, blank composer, pending write, or unknown outcome. Ctrl/Cmd+Enter submits from composer/edit; Escape closes/cancels edit/delete; focused heading on mount.
- Comment edit is revision qualified; external revision conflict shows current saved Markdown and Keep mine / Reload (discard my edit). Cancel says “Cancel / keep edit”. Deleted-elsewhere dirty edits are preserved and offered “Post as new comment” or discard; repost uses captured todo ID, writes a new comment, rekeys post-save typing to new returned comment ID. Task removed state explicitly says comments/drafts are kept; posting requires a current todo, but edit/deleted drafts can remain visible.
- The key uses `todoId` and component key causes detail remount on different selected task, while the drafts store remains Notes-UUID scoped. This is source identity capture, not proof of runtime behavior.

### N-REC-06 — Decision edit/new/replacement drafts
**Sources:** `src/app/notes/Decisions.tsx:8-57` (state, async list/get and reconcile); `Decisions.tsx:58-101` (new/edit mutations); `Decisions.tsx:104-117` (controls/conflict output); `src/app/notes/RetainedDrafts.tsx:9-29` (orphan decision edit). Protocol response IDs/revisions: `crates/cockpit-protocol/src/notes.rs:307-339`.

- New decision draft is shown on mount if present. Create/replacement writes are blocked for blank title, duplicate in-flight create, unknown outcome, or replacement whose source is missing/replaced/revision-changed. Confirmed response selects returned decision and deletes draft only if title/body/date still match submitted snapshot; otherwise leaves changed draft.
- Existing decision edit is keyed by decision ID; selected decision detail read reconciles title and body independently against same summary revision. Mutation uses current record revision for Keep mine; otherwise uses dirty body revision when body changed, else title revision. Conflict blocks normal save if either field conflicts; confirmed response acknowledges both fields, retaining typing newer than submission.
- List is debounced 160ms; loading and per-view error state; current/history filter and query; when query has no results in selected status it queries other status for an “other matches” indication. Detail GET errors clear detail record and show error.
- Missing decision edit remains in RetainedDrafts with source ID and copy-selectable title/body plus explicit discard; no guessed replacement target.

### N-REC-07 — Unknown write outcome acknowledgment gate
**Sources:** `src/app/notes/useNotes.ts:30-33,98-114` (`notesMutationError`, `mutate`); `src/app/notes/NotesView.tsx:70-90` (check/read proof and acknowledgment); `NotesView.tsx:152-155` (warning, buttons, alert); `src/app/notes/notesState.test.ts:94-107`; `src/app/notes/NotesView.behavior.test.tsx:1-25,149-155,175-220` (real consumer/mock-renderer setup, guarded-write assertions, read/acknowledgment/incident/remount assertions; source inspected, tests not run).

- Unknown outcome incident is retained in UUID-scoped draft storage, not merely component-local state. On remount it initializes model error from saved incident (`useNotes.ts:43-51`). Writes of all Notes consumers share model guard. The visible warning explains draft kept, read current state before next write, and possible duplicate posting. “Check saved state” refreshes documents and selected todo comments; successful check associates transient proof with exact incident message. Explicit acknowledgment clears guard; check failure updates error but does not prove. A later uncertain operation creates new incident and resets proof.
- The refresh shown is broad scratchpad/todos/decisions plus selected todo comments; comments for other tasks are not necessarily part of read proof. No automatic write retry is present in inspected code.

### N-REC-08 — UUID scoping, backend revision/atomicity and protocol boundary
**Sources:** `crates/cockpit-core/src/notes/fs.rs:19-40,60-67` (unknown errors, SHA-256 revisions, UUID validator); `fs.rs:161-216` (safe bounded read); `fs.rs:218-286` (publish/remove); `fs.rs:288-329` (lock); `crates/cockpit-core/src/notes/registry.rs:104-149,172-218` (registry corruption checks, catalog, resolve); `registry.rs:219-278` (binding); `registry.rs:339-374` (change tokens); `crates/cockpit-protocol/src/notes.rs:61-175,242-281,312-339` (selector, operations, UUID target/document types); `crates/cockpit-core/src/notes.rs:117-120,186-261` (request dispatch, pinned lock and response notes ID).

- Notes target IDs are canonical lowercase hyphenated UUID strings; filesystem `validate_uuid` parses then requires canonical `Uuid::to_string()` equality. Registry validates IDs/bindings; catalog only accepts UUID-named directory entries. Space target association resolves/binds a Notes UUID; direct Notes target dispatch validates UUID. Target response includes `notes_id`, folder, optional Space and separate scratchpad/todos/decision/comment change tokens.
- Reads reject symlinks/nonregular files, enforce size, UTF-8, and return SHA-256 revision; absent file has revision `absent`. Publish writes unique UUID-named temp file, syncs it, compares destination base revision and optionally source decision revision, renames and syncs directory. Conflict is explicit; uncertain file/rename/sync failures return `notes_outcome_unknown` instructing re-read, no blind retry. Lock is exclusive with bounded 5s retry. Protocol mutation selectors explicitly carry expected revisions for ID selectors and document/comment/decision operations.
- Change tokens combine metadata for scratchpad/todos and collection tokens for decision/comment collections; Notes client polls tokens to refresh. Protocol is a typed boundary: `NotesTargetInfo` includes exact Notes UUID; documents include revision.

**Conservative contracts:** UUID identifies Notes folder; do not substitute current Space label/session identity for captured Notes UUID on an outstanding mutation. CAS revision conflict means reread, never silently upgrade expected revision. `notes_outcome_unknown` is not success or failure; inspect durable state and require user’s explicit recovery acknowledgment before another mutation.

### N-REC-09 — Persisted view state, focus/navigation and source path affordance
**Sources:** `src/app/notes/NotesView.tsx:17-33` (`ViewState`, defaults, `readSurface`); `NotesView.tsx:35-53` (Notes content and persistence effect); `NotesView.tsx:70-111` (saved-state check and details selection/focus); `NotesView.tsx:127-151` (tablist and panels/detail mounting); `NotesView.tsx:152-161` (errors/recovery/retained drafts); `src/app/notes/notes.css:58-62,227-255` (save state, retained draft layout).

- View key is `cockpit.notes.surface.v1:${notesId}` and in-memory map is likewise keyed by Notes ID. State fields are tab, selected todo, selected decision, hide-completed, detail-open. Default is Kanban/no selections/show completed/details closed. Invalid/missing JSON falls back to default; valid data checks known tab, nullable string selection IDs, boolean hideCompleted; `detailOpen` is true only when exactly true. LocalStorage write failures are swallowed with comment that draft storage has a separate visible warning. Drafts and view preference are separate persistence records.
- Tabs expose `role=tablist/tab/tabpanel`, selected tab is only tab stop (`tabIndex 0`, other tabs -1). Left/right cycles tabs, Home/End jump, focus follows tab change. Panels use `hidden`. Todo source popover exposes read-only `folder/todos.md` and click-to-select path.
- Opening detail records invoking element. Closing detail returns focus to connected opener, else add-todo/add-card input; detail mounts only for selected task and todo/kanban tabs. Comments heading receives focus on detail load. Task-detail Escape and Ctrl/Cmd+Enter actions are described in N-REC-05.

## Evidence-backed UX risks / review observations (not proposals)
1. **LocalStorage read failure is indistinguishable from no saved draft at first read.** `drafts.ts:43-74` catches all read failures and returns empty defaults, while only write failure is surfaced. Evidence supports potential draft loss visibility gap; actual browser failure behavior not exercised.
2. **Orphaned source recovery is gated by scratchpad availability.** `RetainedDrafts.tsx:5-6` returns null when scratchpad absent, although retained todo/decision drafts may exist. This can hide recovery during scratchpad read failure or before scratchpad has loaded; code only, runtime not proven.
3. **Unknown-outcome saved-state review is broad for core records but comment verification is only for currently selected todo.** `NotesView.tsx:68-87` refreshes scratchpad/todos/decisions and optionally reads selected todo comments; other comment threads are not explicitly re-read in that proof path. The guard is released only after explicit user acknowledgment; potential review ambiguity for an incident on a different todo is source-derived.
4. **Persisted selected todo may refer to missing task.** `selectedTodo` is accepted as arbitrary string during state parse and detail resolves by ID only (`NotesView.tsx:24-33,91,127`); removed task can still mount removed-task detail if selected ID is retained, but selected row highlighting may disappear. This may be intentional recovery, not runtime proof.
5. **View-state browser persistence errors are silent by design in this code.** Surface state remains in memory map, but unlike draft storage no visible warning appears (`NotesView.tsx:49-51`). This is a durability expectation distinction, not evidence of user-reported impact.
