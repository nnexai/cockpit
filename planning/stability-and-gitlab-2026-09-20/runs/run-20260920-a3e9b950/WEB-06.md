## Per-process attribution run — memory plateau remains open

A second unchanged-product native run (`native-6767304d9028`, fixture `?sustained=335`) again passed DPR2 first bitmap, 19,383 paints / 335.0043 seconds = 57.86 FPS, final `scrollY=3900` with painted green marker, zero static idle paints, and all owned process/port cleanup. It recorded 339 one-second samples; 309 post-warm-up samples span 30–338 seconds. `WEB-06-native-samples-per-pid.json` holds each sampled PID, process `comm`, Linux `/proc/<pid>/stat` start tick, PSS, and CPU tick (485,783 bytes; SHA-256 `91752b67cf6216391dc10eefa32d889bb07d94aed053d092bd82c3ce773af822`). No command lines, credentials, or profile bytes are logged.

The same nine sampled processes remained live throughout. Aggregate PSS was 461,491→535,773 KiB, median 499,485, p95 534,010.6, slope **+241.52 KiB/s**; second-run CPU median 46% and p95 50% of one core. By stable `(PID,start_ticks)`, the WebKit web-content process `166549/26248290` grew 191,934→254,592 KiB (+200.32 KiB/s); its final 60-second slope remained +193.01 KiB/s. The WebKit network process `166528/26248283` grew 23,538→33,416 KiB (+35.93 KiB/s; final minute +13.22). Native Tauri `166480/26248271` remained 129,864→130,032 KiB, gateway `166102/26248050` 26,350→26,382 KiB; Herdr, compositor, runner, and WebDriver controller did not account for the large increase. The second run corroborates non-plateauing WebKit memory rather than proving an application leak or a WebKit cache cause. The sampler covers its explicitly owned process trees; a detached external Chromium/helper would not be included in these nine-process totals.

No speculative WebKit/Blob/GC mitigation was shipped: `FramePresenter` currently closes `ImageBitmap` and revokes fallback object URLs in `finally`, and the remaining cause is not isolated by these PSS samples. WEB-06's five-minute **paint** and static-idle criteria passed, but its memory-plateau, decoded-object/queue ledger, slow observer, crash/reconnect, owner/observer lifecycle, and full browser/native matrix remain blocked. A later run must distinguish retained decode/transport objects from engine memory before claiming a resource fix.
