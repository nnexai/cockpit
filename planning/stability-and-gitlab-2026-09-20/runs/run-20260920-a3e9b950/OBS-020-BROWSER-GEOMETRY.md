# OBS-020 — stabilize browser input and first frame across geometry changes

Date: 2026-09-23. Linux native run at 2× scale. Fractional scaling and macOS were not tested.

## Findings and repair

The DPR 2 native reproduction showed two state transitions behind the reported behavior:

- Chromium input coordinates use host-device scale on initial attachment and again after a main-document loader change; a real emulated viewport resize switches dispatch coordinates to CSS pixels. `browser-helper.mjs` now tracks that mode, scales pointer, wheel, and held-button release coordinates at the CDP boundary, switches to CSS coordinates after an accepted viewport-size change, and restores the DPR scale on a new document.
- A resize restarted the screencast but did not request a frame. With a static page, viewport metadata advanced while the last frame still described the old dimensions until another page event caused paint. Resize now captures a frame immediately after restarting the screencast.

### Capture transport correction

The first helper implementation was rejected by native integration, not shipped as the outcome above. A temporary helper diagnostic in two fresh preloaded fixtures recorded a 583×649 screencast frame at DPR 2, followed by a 1166×1298 direct screenshot after reapplying the same metrics, followed by another 583×649 screencast frame under the same document/viewport/capture token. The first high-density screenshot briefly passed the startup gate; the next low-density screencast overwrote it. Repeating metrics does not make Chromium's screencast output stay dense. Reviewer additionally found that a capture-token change could prematurely complete the gate, while page rebinding could leave it stuck repairing.

The revised capture contract is event-driven: ACK and withhold every undersized screencast frame at DPR 2, use screencast activity only to schedule a bounded direct screenshot, and publish high-density screenshot pixels only when fresh layout metrics **before and after** capture match the pinned target/document/viewport/capture token and scroll/visual geometry. No screenshot may borrow an older screencast's scroll metadata. One screenshot operation is active at a time; stale or ambiguous captures are discarded. This is a stable-geometry bracket, not an atomic pixel-plus-scroll receipt. If it cannot keep user input/annotation geometry safe under a real scroll or deliver a sharp first frame without a gesture, it fails this increment and needs a different capture mechanism. No frontend zoom or observer takeover is allowed.
