Supervisor as liaison

1. Outcome and boundaries

A task continues through CLI replacement, conversation rollover, Cockpit interruption and a proven machine reboot without becoming a new task or a new approval exercise. One start request delegates work; the worker chooses ordinary implementation steps, uses its own subagents and returns committed output with affected checks. The liaison coordinates dependencies, acceptance and integration. The existing private owner resumes work and cleans eligible managed resources without waiting for the root conversation.

In scope: the whole retrospective

Relaxed bindings and recovery; liaison and worker autonomy; one start; mutable scope; quiet delivery; deterministic shared-resource scheduling; source/integration separation; proportional verification; useful batching; automatic resource cleanup; observational UI; bounded learning from the result.

Not a new platform

No extra daemon, mandatory companion context, dashboard, composer, approval hierarchy, build-command executor, metrics product or proof infrastructure. No global OMP setting changes. Herdr remains the runtime resource authority; canonical task Markdown remains the task authority.

Scope: PLAN.md:5–9, PLAN.md:152–167; UI exclusions: UX.md:7–18. Current authority split: CONTEXT.md:80–92.

3. Decisions: fewer primitives, clearer meaning

Everything described as a target below is proposed. Concept labels describe required information and effects, not existing Rust types, wire actions or runnable CLI commands. Exact API spellings must be generated through the repository's existing protocol path, not copied out of these diagrams.

The job is durable; its execution attachment is replaceable

Durable work

Keep across restart

Root / run / task identity
Who owns the work and which canonical task it serves. A new conversation is not a new task.
Canonical scope and history
Task Markdown, checklist, scope revisions, decisions, unanswered questions and explicit Results.
Checkout and resource ownership
Current exclusive managed writer claim; owned versus borrowed resources; creation-time cleanup authority.
Output, integration and uncertain effects
Accepted committed output, target mapping and verification, delivery operation IDs, cleanup intentions and per-effect outcomes.

Replaceable execution

Observe and reconcile

OMP conversation and executable
A compatible installed CLI is a transport client, not the source of the job's right to continue.
Process / launch identity
PID, process start, launch attempt and boot identity help establish what is actually alive.
Herdr endpoint and location
Session, Space, tab, pane and terminal are physical attachment evidence, not durable permission to recreate work.
Runtime observations
Liveness and readiness are observations. Missing or old observations do not prove a process has exited.

A checkout claim is not an expiring permission to overwrite. An offline worker may still be editing. Missing heartbeat, expired TTL, changed endpoint or an unavailable machine does not authorize a replacement writer. Actual handover or proven exit is required.

The existing canonical Markdown/store split stays. The new private, role-scoped job credential authorizes orchestration calls; it does not make local shell execution dependent on a live owner. Credentials never enter task Markdown, progress, logs or UI diagnostics. This is same-user accident prevention, not a sandbox against arbitrary same-user writes.

Proposed model and fence: PLAN.md:32–48. Current store boundaries: CONTEXT.md:56–59; current atomic-store/no-exactly-once caveat: DECISIONS.md:135–137.

Rejected alternatives

  • Cache the old per-tool gate: rejected because local work would still depend on a cached permission model and eventual transport checks. Remove the gate; authorize actual orchestration API calls.
  • Use heartbeat expiry as ownership transfer: rejected because disconnection does not stop filesystem writes. Reattach or establish quiescence.
  • Keep Prepare/Execute but hide them: rejected because invisible ceremony still consumes model time and blocks plan changes. One task-level start replaces both.
  • Give every extraction a private product environment: rejected because the changed contract, not the touched subsystem, determines verification. Integrate and exercise a mechanical batch once.
  • Make source acceptance imply integration or deletion: rejected because accepted output may still exist only on its branch, and later work may not be covered by a prior integration record.
  • Make Finish cleanup the normal completion step: rejected because ownership belongs to the runtime, even without a root model. The action only retries that same safe operation.
  • Import Firstmate's full policy stack: rejected because role separation and benign-wake suppression are useful; another exact-plan/ACK/approval hierarchy is not.

Decisions elaborated from PLAN.md:30–89 and UX.md:217–228; no additional approval requirement is introduced.

Lifecycle transitions: progress is not permission

Admission → start
A durable start request binds task, scope, placement and ordinary cleanup authority. The dispatcher checks prerequisite readiness and checkout ownership, then launches idempotently. Placement uncertainty is resolved by the liaison; it does not create a permanent Scoping or Ready lane.
Starting → Working
Actual connection and startup observation establish the worker attachment. A launch ACK alone does not establish a usable actor. The same start operation advances; no new exact-plan Execute request is required.
Working → Review → Done
Only an explicit successful source Result and its review can lead to acceptance. Idle process, completed checklist, transport ACK and green runtime status are insufficient. Scope/version conflicts remain visible; a stale replay cannot accept a newer task silently.
Send back / new work
Send back retains meaningful review semantics. Ordinary pre-acceptance refinement does not replace the worker. Accepted history stays protected; a genuinely new outcome is new work, not a rewrite of the accepted result.

Target: PLAN.md:42–68; UX.md:124–146. Baseline explicit-result distinction: CONTEXT.md:90.

Interrupted recovery decision tree

Offline means offline all the way through the extension: session_start, session_switch and before_agent_start binding refresh use quiet, bounded background retry. A cached job brief and durable outbox allow ordinary local editing, checkpointing and committing while the owner or CLI is unavailable. No manual exact-SDK-session rebinding workaround is part of the product path.

A currently available compatible CLI is resolved with an explicit protocol-version check; incompatibility yields one useful transport error, not permanent job invalidation or a repeated local-tool block. Background retry is recovery, not a claim that an orchestration mutation succeeded offline.

Three independent facts, two readable UI segments

Source

What was accepted?

Explicit worker Result, committed output and focused checks. Review is not yet acceptance; acceptance is not a full-product smoke.

UI: Review → Done · source complete.

Integration

Where did that output go?

pending, integrated with output-to-target mapping and changed-contract verification, or not_applicable for non-code work.

UI: Outcome names source complete or integrated.

Cleanup

What resources remain?

Per-resource intent and outcome. Worker, Git resources, Space, scratch and fixture set may have different eligible effects.

UI: Cleanup remains a separate text segment.

Example: accepted output A maps to target commit T and passed the relevant integration checks. Later, the worker branch gains two new commits B and C. The task's accepted output is still integrated, but B and C are not covered by that fact; branch and worktree stay. “Integrated” describes accepted output, never all future content of a mutable checkout.

Integration record semantics — proposed data contract, not an existing API
Accepted output identity
Name the accepted Result and its exact committed output within the task/run. A subsequent task or source revision cannot silently inherit the record.
Target identity and mapping
Retain target reference/commit and the relationship from each accepted output to the target output. A target commit without this mapping is incomplete evidence.
Method
ancestor: accepted output is included by history. patch_equivalent: deterministic patch equivalence establishes equivalent output. recorded_adaptation: the integrator explicitly supplies a verified output-to-target mapping for adapted changes. Runtime validation checks that record; it cannot infer the adaptation from a hash, source acceptance or a “merged” label.
Changed-contract verification outcome
Preserve what was actually checked on the integrated artifact, the result, and any unrun limitation. Source checks are not silently promoted to integrated checks. Incomplete or contradictory verification must not be presented as successful integration merely to enable cleanup.
Cleanup consumption
Re-observe repository/checkout identity and all additional dirty or unmerged work since the receipt before deletion. not_applicable is for non-code deliverables; it is not an escape hatch for coding in a borrowed directory.

Mutable plans, quiet messages and a small resource queue

Scope is mutable; history is not disposable

Existing Follow-up to agent becomes one durable operation: update canonical task description with normal task/document CAS and deliver an instruction to the same worker. If delivery is interrupted, preserve the original operation ID and draft; reconcile that operation instead of sending a different duplicate.

A worker's own refinement updates its advisory scope without sending an instruction back to itself. Root/operator updates while Working are allowed within scope; accepted results remain protected. There is no Amend-scope form, exact-plan reapproval or successor actor just to change an implementation step.

Progress is a snapshot; a decision is an event

Latest progress replaces latest progress. Scope changes, questions, answers, Results and acceptance retain meaningful history. Extension/runtime consumes durable messages and advances transport cursors; a coalesced digest wakes the model only for actionable changed state.

Transport consumption never answers a question. An explicit answer retains its question link; “answer delivered” does not establish that the task resumed or its question was semantically resolved.

Outbox and cursor boundaries — interruption cases workers must implement
  1. Before owner delivery: persist the outgoing operation locally with stable identity and original payload. A disconnected report is pending delivery, not accepted.
  2. After delivery, before local confirmation: replay the same operation ID. Receiver deduplication preserves one semantic operation, including after restart; changed payload under that identity conflicts rather than silently overwriting.
  3. After receive, before cursor advance: extension resumes durable consumption without losing the actionable instruction. Cursor/receipt bookkeeping must not manufacture a second task update or model answer.
  4. After scope or ownership changes: apply current task/version and checkout-claim checks. Replayed Result may conflict; retained output and one useful conflict are safer than implicit acceptance or conflicting takeover.
  5. Unknown external effect: do not generalize message replay into replaying launch, stop or remove. External-effect reconciliation remains its own boundary.

These are semantic boundaries, not a promise of globally exactly-once external effects or a new general message broker. Reuse the existing store/intents and operation identities.

Artifact identity must match the actual source/input used. Safe dependency caches may be shared; incompatible worktree outputs may not be blindly reused. One integrator build for a mechanical batch is preferred over private frozen host/native pairs per worker. Batch adjacent small extractions into one worker checklist unless independent ownership or a useful standalone outcome justifies a split. Function-size counts guide planning, not acceptance.

Coordination and queue: PLAN.md:50–72; UX uses existing form and details: UX.md:138–146. No claim is made that this product queue exists today.

Minimal UI primitives, not a redesigned dashboard

Keep terminal-chat work entry and Tasks / Graph / Dependencies. Reuse the Summary shortcut slot, attention rows, existing forms, card status and Overview details. The examples are isolated static fragments; outlined labels are text, not working buttons. Colors here serve document readability, not a new product token specification.

Interaction semantics retained from UX

  • Start / Show: select the already-selected matching root, otherwise the most recently active matching root. Reuse a live root; resume a stopped root. Initial Start creates a root only when none exists for the project. Start another agent… explicitly creates an additional root through the existing Name/Location dialog. No new shortcut or top-bar button.
  • Attention: routine grants, ACKs, slot contention, worker-local questions and verification never become user prompts. Genuine outcome/tradeoff/new-commitment choices become root Decide. A recognized writer reconnects silently; only an unresolved live-writer Keep/Replace tradeoff is Decide. Unreachable Herdr, changed checkout or an unconfirmed effect after recovery attempts is Recover.
  • Follow-up: same textarea, Send, scoped draft and Retry same message identity. Success reads “Update sent · task description updated.” Activity shows read-only Scope. No armed Prepare/Execute override or new Amend control.
  • Cleanup states: running, waiting, waiting for integration and reconnecting are quiet. Kept user work is Notice; stalled automatic cleanup is Notice with optional Finish cleanup; unknown outcome after retry is Recover. Plain causes, not PIDs/hashes, explain the result.
  • Inspection: Overview gains a Cleanup group. Advanced retains explicit result acceptance, Send back, Close tracking and Diagnostics; opening it grants nothing. Done stays collapsed; only an explicit Show in Tasks reveals it. Graph still omits completed tasks and adds a kept count.
  • Removal distinction: Commands “Finish task cleanup” retries pending records without a dialog; Pending cleanup becomes an inspection list with that retry. User-initiated Space-menu “Review task cleanup…” keeps the typed REMOVE <path> safeguard. The automatic route does not inherit a new typed-confirmation ceremony.
  • Focus and drafts: automatic updates never move focus, scroll, select or expand. Explicit Open terminal is the terminal-focus action. User-invoked Start/Resume retains the existing invoker-aware restoration; if the user moved focus, do not move it back. If an action row disappears, use the existing nearest-surviving-row rule. Answer, follow-up, note and send-back drafts survive reconnect, root switch and hide/return; terminal text is never submitted or cleared by cleanup.
  • Accessibility: one polite coalesced product status region; routine progress unannounced. Recover and failed user actions use alerts; kept work uses status. Verb labels, disabled reasons and existing dialog Tab/Escape rules remain. Narrow windows stack the existing Cleanup list; no extra responsive surface.

Interaction authority: UX.md:79–215, UX.md:260–275. Static fragments intentionally contain no forms, buttons, scripted handlers or fake operation links.

4. Open questions: no new product choice required

The proposed architecture uses the following explicit interpretations so workers do not reconstruct contradictory behavior from a compact example or an old current-product rule.

Live writer: automatic reattach versus Decide versus Recover
Recognized living managed worker → reattach automatically. Genuinely conflicting writer that cannot be reconciled and needs a Keep/Replace tradeoff → Decide. Unreachable runtime, externally changed checkout or unknown-effect retry failure → Recover. UX §4.4 uses this distinction; no routine Resume dialog or TTL permission is added.
Integrated task with an unmerged branch
Integration applies to the recorded accepted output. Later source is retained separately. UX §11 and the static fragment here explicitly distinguish the integrated accepted output from later commits that still protect the branch/worktree.
“New root only via Start another”
The restriction concerns an additional root when a matching root already exists. Initial Start still creates a root when there is none; Show/Start does not silently multiply roots.

Remaining evidence probes are implementation prerequisites, not policy questions:

  • Project lookup: use recorded source-project/repository identity, not process cwd, labels or a UI guess. Current orchestration.rs:229–254 exposes target Space, repository identity and optional project_workspace_id; the latter is explicitly absent for non-SpaceWorktree targets. The wave-1 contract owner must trace all start/adopt/setup targets and publish one host-owned lookup contract. Do not pretend that optional field alone is already a complete “same project” key.
  • Missing-Space cleanup adapter: inspect current supported Herdr/Git adapter behavior before selecting the call path. Use supported local Git cleanup with the same ownership/concurrency checks if the Herdr path requires a live Space. Do not invent an upstream endpoint, raw-command fallback or new user ceremony. This probe belongs before wave 4 effects are implemented.
  • Exported callers and active storage shape: use actual references and representative persisted records before changing schema. The owner inventory is a map, not an exhaustive reference result. Unknown records or attachment evidence remain retained, not guessed into a cleanup-eligible state.

These probes are already required by PLAN.md:105–117 and PLAN.md:87; project lookup is identified as an inference in UX.md:93–96. No unsupported API is specified here.

5. Delivery slices: five coherent waves

Each wave changes a usable vertical contract, not a model approval stage. Shared Rust DTOs/store/projection and generated contracts have one wave owner at a time. Parallel workers consume fixed interfaces; they do not independently edit the same facade or invent alternate schemas.

Wave 1 · Durable execution and unattended resume

Goal: the same task and checkout survive replacement of CLI, main conversation and runtime attachment without duplicate writers or loss of local work.

Exclusive ownership
Protocol/store attachment and claim contract; core orchestration.rs, caller.rs, mutate/runs.rs, mutate/reviewed.rs; host CLI caller.rs/context.rs and runtime dispatcher; OMP identity.ts, cliCall.ts, main binding and extension.ts. Exact owner inventory below.
Fixed interface
Durable job/role credential; replaceable attachment; one checkout writer; idempotent resume; current compatible CLI routing; host-owned root-for-project lookup. Fresh process/pane checks stay at physical effects, not local tool permission.
  1. Trace exported references and stored attachment/target variants; retain root/task IDs and checkout ownership.
  2. Implement private role-scoped credential authorization and atomic claim handover. Preserve operator origin and cross-root boundaries.
  3. Implement reattach-first recovery, same-machine boot proof, verified cooperative handover and uncertain-effect reconciliation in the existing owner.
  4. Delete the global tool-call gate. Make session/turn binding refresh quietly retry in the background; cached brief/outbox permits local work when CLI/owner is absent.
  5. Resolve a compatible current CLI without pinning the job forever to a removed launch executable. Return a useful incompatibility cause; no global installation/settings changes.

Non-goals: replacing Herdr, a new daemon, actor replacement for scope edits, a security sandbox, lease-expiry takeover.

Acceptance: cases B/C/D. Change CLI and main conversation, disconnect the owner, then restore it; observe continued local editing/commit and the same task/checkout. Reattach a living writer without a dialog. Deny duplicate launch while the old writer lives or its exit is unproven. Native attachment/effect changes require the corresponding disposable native path later.

Wave 2 · One start and autonomous liaison

Goal: one task-level request reaches source results, and ordinary scope refinement stays with the same worker.

Exclusive ownership
Protocol actions/stages; core mutate/grants.rs, mutate/dispatch_records.rs, messages/report.rs, mutate/tasks.rs, prerequisite/intents/projection; CLI args/subcommands; OMP management tools and guidance. Serial handoff of shared files from wave 1.
Fixed interface
One start request includes scope, placement, prerequisites and normal scoped cleanup authority. Readiness is observation. Task/document CAS remains; root/operator Follow-up updates task and delivers one instruction. Worker self-refinement has no self-message. Accepted history remains protected.
  1. Replace Prepare/Execute with the start-to-working lifecycle and remove plan-equality permission checks and obsolete actions.
  2. Preserve actual launch observation, canonical prerequisite checks and idempotent dispatch under the new lifecycle.
  3. Implement Working scope updates as recoverable task/message intent, including unchanged retry identity and conflict outcomes.
  4. Update worker/root brief guidance for autonomous local command choice, subagents, proportional checks and useful batching; remove routine grant questions.
  5. Expose backend Start reuse/resume semantics and explicit additional-root creation for the existing UI to consume.

Non-goals: a new composer, new Scoping/Ready lane, widened external commitments, making every instruction an answer.

Acceptance: cases A/E. Two workers and local subagents reach source results without routine grants; a Working Follow-up changes canonical scope and reaches the same actor once. One genuine outcome-changing ambiguity reaches the user. Accepted task history cannot be silently amended.

Wave 3 · Quiet transport and integration-sized verification

Goal: machine bookkeeping no longer fills the model conversation, and combined verification is recorded separately from source acceptance.

Exclusive ownership
OMP wake.ts, inbox/message tools and durable local outbox; core messages.rs/messages/inbox.rs publication; host wait/notification and owner resource queue; result/integration DTOs, mutate/intents.rs, projection and worker/root briefs. One protocol/projection owner serializes shared changes.
Fixed interface
Stable operation IDs and durable delivery cursors; explicit question/answer links; latest-progress replacement; required integration fact with accepted-output mapping and verification outcome; FIFO-ready resource keys with verified holder release/abandonment. No build-command payload.
  1. Land the integration data contract and runtime validation first, including explicit verified adaptation mapping; make it available to wave 4.
  2. Move receive/ACK bookkeeping into extension/runtime, coalesce actionable changed-state digests and preserve semantic Results/questions.
  3. Persist and replay outbox operations through interruption boundaries without duplicate semantic writes or stale-result acceptance.
  4. Use revision notifications; retain only a bounded liveness/cross-process fallback. Unchanged observations do not rebuild full snapshots or wake the model.
  5. Add resource request/release scheduling to the existing owner. Workers/integrator execute their own builds; artifact identity and living holders remain protected.
  6. Make mechanical-batch briefs request focused source checks, followed by one combined integration build/affected smoke. Keep real contract/native/external-service checks where changed.

Parallel opportunity: after interfaces land, OMP transport, owner queue and integrator-result wiring can proceed in disjoint files. Shared protocol/projection edits stay with one owner. Wave 4 can start against the integration fact while independent transport work finishes.

Non-goals: a general broker, model build-slot approvals, per-worker proof projects, new quality/mutation thresholds.

Acceptance: cases B/F/G/H. Interrupt between delivery and cursor advance; one operation remains. Deliver a question without answering it. Repeated unchanged status causes no repeated model wake. Competing builds do not share incompatible artifacts or steal a live holder. Accepted source is not labeled integrated until its required mapping/check outcome exists.

Wave 4 · Autonomous resource cleanup

Goal: the owner, not the root conversation, retires finished workers and safely removes eligible owned resources, including historical drift and fixture sets.

Exclusive ownership
Core retirement and project teardown/ownership records; host orchestration_runtime/retire.rs, dispatcher and project adapters; scoped cleanup CLI/tool/shared transport. Integration schema remains owned by the wave-3 contract owner until handed off.
Fixed interface
Standing creation-time owned/borrowed authority; per-resource intent/outcome; same idempotent subtree cleanup for owner and optional retry; integration mapping consumed as evidence, not inferred; one fixture resource set with normal shutdown and per-effect outcomes.
  1. Inspect actual supported missing-Space/worktree adapter semantics; select existing supported Herdr or local Git paths with the same identity/ownership safeguards.
  2. Register resources at creation, including fixture sets and generated scratch classification. Remove the root's blanket “Never tear down resources” prohibition.
  3. Implement independent eligibility for process/tab, worktree, branch, Space, scratch and fixture set using the cleanup table above.
  4. Reconcile stale endpoints, proven same-machine reboot and equivalent ownership receipts. Preserve genuine conflict and user/foreign state with a compact reason.
  5. Persist intent before effect, observe actual state after interruption and record each outcome. Never replay an unknown stop/remove blindly.
  6. Run cleanup on completion/cancellation, startup, reconnection and changed eligibility. Expose Finish cleanup as a retry of that same operation, not a separate force path.

Non-goals: deletion of borrowed/unmerged/unknown resources, broad process kills, per-fixture model closure protocols, cleanup that waits for the root to ACK.

Acceptance: cases H–L with root model offline. Accepted-only output survives; integrated eligible resources disappear; adapted mapping is validated; later commits, drafts, borrowed Spaces and live/foreign consumers survive; normal fixture shutdown precedes scratch deletion. Interrupt an effect and observe reconciliation without a repeated destructive operation.

Wave 5 · Surface cutover and existing-job continuity

Goal: expose the completed contracts through existing UI and installed clients, preserving work created before the cutover.

Exclusive ownership
Supervisor hooks/actions/attention/lanes and dialogs; Commands and task-cleanup surfaces; browser/native decoders and generated TypeScript integration; final active-record conversion in the store; current docs and portable OMP guidance. Conversion design starts with wave 1, not after automatic effects ship.

Operation semantics to fix before parallel caller work — names are conceptual
  • Resume: same durable run/task/checkout; idempotent reattach or one verified replacement; stable cause when blocked; no Prepare/Execute. It is not a blind launch retry.
  • Start / project lookup: host resolves matching recorded project; selected matching root wins, otherwise most recently active; additional-root creation is explicit. UI supplies intent, not a guess based on cwd or display name.
  • Scope update: expected task/document revision plus stable operation identity; update canonical task and enqueue one instruction durably; expose original unknown operation, not a false failure that encourages a new duplicate.
  • Integration report: accepted-output identity, target mapping/reference/commit, method, changed-contract verification outcome. Adaptation is supplied by the integrator and validated by runtime. Coding in a borrowed path never means not-applicable.
  • Resource request / release: resource key and holder identity; FIFO-ready scheduling and verified abandonment; worker-owned build execution. No arbitrary shell payload or model approval.
  • Cleanup retry: subtree-scoped repeat of safe reconciliation; per-resource outcome with a reason, not a force flag or per-resource destructive selection. Fixture normal shutdown is one owned-set operation with internal effect receipts.

UX shorthand such as run resume, Run.integration and CleanupFinish names proposed contracts. This document does not claim those are existing commands, fields or wire symbols. The protocol owner assigns exact schema through the existing Rust-derived pipeline.

Existing active-job conversion: continuity, not permanent compatibility

  1. Read and stage under the existing store discipline. Design conversion alongside the durable model. At the release boundary, prevent mixed-schema dispatch and make conversion atomic/resumable using the existing locking and intent pattern; do not invent a second task store.
  2. Preserve durable meaning. Keep task/run/root IDs, canonical content, committed output, checkout/resource ownership, unanswered questions, pending messages, stable delivery IDs and uncertain-effect receipts. Never turn “unknown” into “absent” to simplify conversion.
  3. Map old preparation to status, not permission. Prepare/Ready/Execute history remains history. Active preparation becomes queued/starting/active status as warranted by actual launch evidence; a ready worker does not need renewed approval. An existing Working task retains its work.
  4. Reconcile before dispatching. Recognize living attachments or prove old writer exit before a replacement gets the checkout. An unknown attachment/ownership record remains preserved and diagnosable. Old source acceptance without a validated integration record remains pending integration, not cleanup-eligible by default.
  5. Resume interrupted conversion/effects from actual state. Preserve external canonical edits and uncertain receipts. A crash between conversion intent and publication cannot duplicate task identity, lose mail or replay a destructive effect.
  6. Cut over callers completely. Once the current schema is active, remove old grant actions, aliases, exact-plan tests and duplicate lifecycle code. No permanent dual implementation; no task/worktree wipe. Update current docs at that boundary, not the historical retrospective.
