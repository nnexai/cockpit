`rankFileMatches` alone in Chromium V8 (throwaway harness, 3-5 runs, median): 3,000 candidates 46-55 ms, 10,000 **111-122 ms**, 50,000 **561-584 ms**, and it is per keystroke, independent of the match count. The plan's earlier "20-80 ms at 10k" **[INFERENCE]** was wrong by ≈ 2×, and the 3k-candidate browser figure (180+ ms) is higher still because of the longer real paths.

**Prepared ranking prototype** (`/tmp/cockpit-perf-rank-browser.ts`, ASCII paths, precomputed folded string and `nameStart`, no per-call allocation, same scoring formula; top-50 identical to `rankFileMatches` on 3 queries): 3,000 → 0.7-2.2 ms; 10,000 → **1.7-2.7 ms**; 50,000 → **8.5-9.4 ms**; one-off prepare 3-18 ms. That is ≈ 40× (3k), 45× (10k) and 60× (50k) faster. It still needs a non-ASCII fallback and match-index computation for the visible rows only.

`ReviewFileTree` duplicates (B11, quadratic `files.some` in `files.filter`; V8): 185 files 0.6 ms, **2,000 files 65 ms per render**, 5,000 files 146 ms; a `Map` count takes 0.3 / 1 / 5 ms.

Disk caveat: `/tmp` is tmpfs, so "read" is a RAM copy. On btrfs a 6.6 MB sequential read is one file; an uncached working-tree walk is ≈ 55k inode lookups. That difference is the case a persisted list is for, and it is **unmeasured** here.

## What contradicts the plan

1. **Repository scan per request is 575 ms at R=72, not 637 ms at R=70**, and the plan's "≈ 2.3 ms per spawn" measured ≈ 2.0 ms. The conclusion (drop the scan from read paths) stands.
2. **Idle burn is the biggest user-visible cost and was not in the plan's numbers**: 12,577 spawns and ≈ 55 % of a core per minute with three panes visible. The plan's "60 s idle ≤ 60 spawns" target is unreachable with a 30 s TTL whole-catalog refill: one refill is 4R = 288 spawns, so 2 per minute ≥ 576. The target is corrected (see the plan §7).
3. **Keystroke ranking is 111-176 ms at 10k candidates in Chromium**, ≈ 2-5× the plan's guess and a top-3 cause of the "sluggish" feeling, independent of the server.
4. **A persisted file list saves ≤ ≈ 80 ms of enumeration on warm caches** (git 86 → ≈ 8 ms at 50k; 10 → 0.5 ms for this repo), because enumeration is cheap. The plan said the same about enumeration; the number confirms it. The remaining argument for persistence is cold-disk and first-open-after-restart, which needs a reboot to measure.
5. **Review fails outright above 1 MiB of diff** (S5 promoted from conditional to required).
6. The picker gets **10,000 of 55,001 files** on `big` and never completes on the real repo: the "index" is truncated today, not just slow.
7. B3's "D=1,000 at R=70: ≈ 80 s wall" **[INFERENCE]** was pessimistic: the scan parallelises, so the throughput is 68 ms per directory request, not 580. The measured 363-dir picker takes 32 s and 5,054 dirs would take ≈ 6 min **[extrapolated]** if it were not stopped at 10k files.
8. B4's "several seconds" for the Library picker measured **43.8 s**, and B5's "N=20k: minutes" **[INFERENCE]** was not measured (N=1,200 → 261 ms).
