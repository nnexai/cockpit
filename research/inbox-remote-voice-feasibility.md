# Inbox remote voice and dictation feasibility

Investigation, 2026-11-08. Scope: feasibility only; no implementation authorized. The installed binary reports `omp/18.18.1`. No real microphone, user session, provider credential, or live gateway was accessed.

## Answer and recommended direction

**Live talk: promising, not yet demonstrated.** OMP's [version-tagged 18.18.1 RPC contract](https://github.com/can1357/oh-my-pi/blob/v18.18.1/docs/rpc.md#live-voice-sub-protocol) specifically exposes `live_connect` for a caller-owned WebRTC peer. This can keep the microphone and speaker on the remote device while OMP controls the live session and delegates work into its own agent session. It avoids a mandatory new speech provider or a host audio loopback. The installed executable's version is observed, but no live RPC call or authenticated provider session was run, so actual installed behavior and provider acceptance are not proven.

**Dictation: feasible in principle, but the same shortcut does not exist in the documented RPC.** `dictation_start` opens the RPC server machine's microphone, not a remote audio stream. A remote-device solution must either extend OMP with an authenticated remote-audio ingestion path into its existing speech engine, use an explicitly selected local/browser STT engine, or introduce an optional external transcription provider. Merely calling `dictation_start` remotely captures the wrong machine. Reuse of the installed engine through an arbitrary input API is not established. Compare each option on implementation and distribution complexity, privacy and model availability before deciding; do not assume cloud STT is required.

## OMP 18.18.1 source contract

The installed binary reports `omp/18.18.1`; the source contract below is the upstream matching version tag, not a binary inspection or a live acceptance result. See [RPC reference](https://github.com/can1357/oh-my-pi/blob/v18.18.1/docs/rpc.md#live-voice-sub-protocol), [live controller](https://github.com/can1357/oh-my-pi/blob/v18.18.1/packages/coding-agent/src/live/controller.ts), [transport](https://github.com/can1357/oh-my-pi/blob/v18.18.1/packages/coding-agent/src/live/transport.ts) and [protocol](https://github.com/can1357/oh-my-pi/blob/v18.18.1/packages/coding-agent/src/live/protocol.ts).

| Function | Contract and implications |
| --- | --- |
| `live_start` | Opens host microphone and speaker; unsuitable for the remote-device goal. |
| `live_connect` | Caller creates an SDP offer with one sendrecv Opus audio track and an `oai-events` data channel; OMP returns the answer once signaling and its control socket are up. The caller applies it and owns echo cancellation and microphone-track muting. No host mic/speaker is opened in the source's SDP mode. The remote mode reports neither `live_levels` nor `speaking` phase. |
| Lifecycle | One live session per RPC server; `live_stop` cancels startup or stops the session. Client must stop OMP when its peer fails/closes, since OMP cannot observe that peer. Transcript frames replace per role/turn until final; a terminal `live_end` is emitted. EOF/shutdown stops the call. Live and dictation exclude one another even during transitions. |
| Credentials | Source uses OMP's `openai-codex` OAuth, model `gpt-live-1-codex`, provider WebRTC signaling and a WSS control sideband; the agent work runs as normal session turns. It uses a provider-internal Codex path and desktop-identifying headers, so service compatibility/policy may change. Linux omits the platform attestation implemented for macOS ARM; acceptance was not checked. Credential availability was deliberately not inspected. This is not the generic OpenAI API-key WebRTC flow below. |
| Dictation | RPC requires `stt.enabled`, uses `modelRoles.dictation` and `stt.language`, emits full accumulated previews and a final `dictation_end` keyed by a unique capture ID, and never submits. Stop may race start and timeout does not cancel the server operation; correlate and insert the final result only once into its originating draft. Default documented local model is Parakeet (~680 MB); model acquisition/cold start and CPU use need measurement. The exact capture plumbing beyond the RPC contract was not inspected. |

### Concrete live integration

Bind the existing or redesigned authoritative Inbox OMP RPC owner to a single live-call generation; don't launch an unrelated session or attempt to attach a second controller to a TUI-owned session without a supported ownership handoff. After a user gesture and permission, the browser creates the peer/track/data channel and sends only the SDP offer through an owner-authorized, origin-checked Cockpit operation to that RPC owner. Return its answer; forward phase, final/partial transcript and terminal events with generation fencing. Mute the actual client track as well as the RPC state, stop the RPC on peer loss or user stop, and handle provider/auth errors without retrying into another conversation. Media goes between the browser peer and the provider; OMP's signaling and sideband stay host-side. Test ICE/NAT reachability and fallback behavior on the real tailnet/mobile network; do not assume Tailscale HTTPS relays the WebRTC media or that UDP is available.

## Cockpit integration boundary

The shared Inbox surface is separate from Workbench and uses the shared client contract (`CONTEXT.md:19-35,68-71`). Its image path (`src/app/inbox/InboxImages.tsx:76-84`) fetches bounded PNG/JPEG blobs, not streaming media. Managed Browser uses JPEG frames and its own WebSocket grant (`src/client/browser.ts:41-45,159-172`; `crates/cockpit-host/src/browser_view.rs:120-143`); its unavailable audio capability describes the managed browser, **not** Inbox voice. Do not flip that capability as a shortcut for Inbox audio. The Inbox has no existing microphone/audio integration found in source.

The gateway is loopback-only and validates Host and Origin (`crates/cockpit-host/src/server.rs:83-90,149-151,176-221`). Native and web clients have different transport boundaries, and the native browser relay has its own narrow origin allowlist (`crates/cockpit-host/src/transport/browser_relay.rs:158-203`). Existing image/frame channels do not establish an authorized bidirectional audio channel. The owner's separate Tailscale deployment is an external HTTPS/identity proxy rather than proof that the product itself has remote authorization; do not weaken its exact owner, Host and Origin checks. These observations are source/configuration guidance, not a live gateway test. The existing runtime redesign must expose a stable session/ownership and cancellation boundary before binding audio; avoid assuming a particular in-flight branch or treating image streams as audio APIs.

## Browser and native device constraints

Capture must happen on the user's device, not just on the Cockpit host. `getUserMedia({audio:true})` requires a secure context (normally HTTPS or localhost) and explicit permission. An unanswered permission prompt can remain pending; denied permission, missing hardware, a blocked permissions policy and an insecure origin need distinct actionable UX where detectable. Embedded frames need appropriate policy delegation; the Inbox top-level surface is preferable to granting microphone access to untrusted widgets. [MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)

Linux native WebKitGTK documents that unhandled user-media permission requests are denied by default. The packaged host must deliberately handle consent; OS device access and actual WebKit media support remain separate checks. On Apple platforms, native usage descriptions and, for sandboxed macOS, audio-input entitlements apply; Safari success alone does not establish that a packaged WKWebView works. [WebKitGTK](https://webkitgtk.org/reference/webkit2gtk/stable/class.UserMediaPermissionRequest.html), [WebKit](https://webkit.org/blog/11353/mediarecorder-api/), [Apple](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSMicrophoneUsageDescription)

## General transport alternatives

- **WebRTC** is a proven browser bidirectional voice transport with echo cancellation and low-latency media delivery; Opus and G.711 are mandatory to implement, not necessarily the negotiated codec. A direct provider connection can use a short-lived credential minted by a trusted backend; this exposes neither the long-lived key nor the host audio device, but does send audio to the provider and is a different integration from automatically reusing OMP's current session. [RFC 7874](https://datatracker.ietf.org/doc/rfc7874/), [OpenAI WebRTC guide](https://developers.openai.com/api/docs/guides/voice-webrtc?api=realtime)
- **WebSocket PCM streaming** gives a host-side bridge control over the OMP/session boundary and keeps long-lived keys server-side; it requires explicit sample format/rate conversion, buffering, flow control, interruption and playback handling. Browser WebSockets use ordered reliable transport, so congestion can add delay. It must not be confused with browser WebRTC or the existing JSON/image streams.
- **Dictation is separate:** push-to-talk, upload a completed recording, and insert editable text is much simpler than full-duplex live talk, at the cost of waiting for utterance completion. Streaming partial transcription offers lower perceived latency but needs turn identification and finalization. Browser `SpeechRecognition` is not a dependable universal fallback and some implementations send audio to their own service. [MDN](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition), [OpenAI transcription](https://developers.openai.com/api/docs/guides/realtime-transcription)

`MediaRecorder` format support must be feature-detected, and its timeslices are not exact; chunks need not each be playable standalone. A browser WebM/Opus recording cannot simply be assumed to be raw PCM or compatible with every STT endpoint. [MediaRecorder](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/dataavailable_event), [format detection](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static)

Latency comprises capture buffering, network, end-of-turn detection, inference and playback; no end-to-end number has been measured. Provider, model, duration and output audio affect cost. Avoid logging or retaining raw audio by default; disclose processing and provider retention. OpenAI's [data controls](https://developers.openai.com/api/docs/guides/your-data) and [pricing](https://platform.openai.com/pricing) are provider-specific and change over time, not guarantees for OMP or other providers.

## Proposed UX and acceptance experiments

Use an explicit user gesture to start either **Dictate** into the currently selected draft or **Start live talk**; never auto-submit dictated text. Show permission pending, active microphone, mute, stop, connecting, interrupted/disconnected and provider errors. Stop local tracks promptly on stop, view teardown, permission loss and failed setup; do not silently reacquire or send speech to a newly selected conversation. Keep a transcript/editable draft with explicit submission and do not treat capture as proof that an agent consumed a message. For live talk support barge-in, stop queued speech when interrupted, visibly distinguish assistant audio from text, and make playback activation possible from a gesture. Backgrounding, mobile audio interruptions and reconnection require explicit device testing.

An implementation proposal should first agree with the runtime redesign on an exact authenticated run/conversation binding, single owner, cancellation, backpressure, rate/size limits and stale-generation fencing. Then implement a shared capture/state UI and narrowly scoped host adapter, maintain native and remote browser authorization separately, and wire the OMP/provider integration selected below rather than adding an unrelated mandatory speech service. Native packaging must request permission deliberately and restrict it to the trusted application surface; do not grant opaque widget/artifact frames microphone privileges.

Verify in disposable fixtures with synthetic prerecorded audio and test-only provider credentials, not the user's live sessions: assert capture-to-text and both audio directions, distinct conversation binding, bounded buffering, interruption and cancellation, denial/no device, delayed permission, duplicate or stale events, disconnect/reconnect, stop/teardown and unchanged drafts. Include negative owner, cross-origin and unauthorized stream tests, logs/retention inspection, an actual packaged Linux WebKit run, remote HTTPS desktop browser and physical mobile Safari/Chrome tests including screen lock and backgrounding. Measure p50/p95 utterance-to-first-audio and final transcription under representative loss and record provider usage and retention. Until then feasibility is architectural, not a demonstrated working product.
