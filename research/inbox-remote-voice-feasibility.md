# Remote live voice: historical feasibility investigation

This is a historical research record, not current product direction or a description of supported Cockpit functionality. Cockpit Voice has been removed; the proposed integration and acceptance experiments below are obsolete. The initial investigation on 2026-11-08 was feasibility-only; the installed binary then reported `omp/18.18.1`, and no real microphone, user session, provider credential or live gateway was accessed. It is not evidence of a successful native or live-provider run.

## Answer and recommended direction

**Live talk: intended, but not yet demonstrated by this investigation.** OMP's [version-tagged 18.18.1 RPC contract](https://github.com/can1357/oh-my-pi/blob/v18.18.1/docs/rpc.md#live-voice-sub-protocol) exposes `live_connect` for a caller-owned WebRTC peer. This can keep the microphone and speaker on the user's device while OMP controls the live session. The installed executable's version was observed, but no live RPC call or authenticated provider session was run, so actual installed behavior and provider acceptance were not proven.

**No Cockpit dictation integration is planned.** Users can use their phone keyboard's dictation. OMP's `dictation_start` opens the RPC server machine's microphone, not a remote audio stream; it is not the Voice screen or a remote-dictation shortcut.

## OMP 18.18.1 source contract

The installed binary reports `omp/18.18.1`; the source contract below is the upstream matching version tag, not a binary inspection or a live acceptance result. See [RPC reference](https://github.com/can1357/oh-my-pi/blob/v18.18.1/docs/rpc.md#live-voice-sub-protocol), [live controller](https://github.com/can1357/oh-my-pi/blob/v18.18.1/packages/coding-agent/src/live/controller.ts), [transport](https://github.com/can1357/oh-my-pi/blob/v18.18.1/packages/coding-agent/src/live/transport.ts) and [protocol](https://github.com/can1357/oh-my-pi/blob/v18.18.1/packages/coding-agent/src/live/protocol.ts).

| Function | Contract and implications |
| --- | --- |
| `live_start` | Opens host microphone and speaker; unsuitable for the remote-device goal. |
| `live_connect` | Caller creates an SDP offer with one sendrecv Opus audio track and an `oai-events` data channel; OMP returns the answer once signaling and its control socket are up. The caller applies it and owns echo cancellation and microphone-track muting. No host mic/speaker is opened in the source's SDP mode. The remote mode reports neither `live_levels` nor `speaking` phase. |
| Lifecycle | One live session per RPC server; `live_stop` cancels startup or stops the session. Client must stop OMP when its peer fails/closes, since OMP cannot observe that peer. Transcript frames replace per role/turn until final; a terminal `live_end` is emitted. EOF/shutdown stops the call. Live and dictation exclude one another even during transitions. |
| Credentials | Source uses OMP's `openai-codex` OAuth, model `gpt-live-1-codex`, provider WebRTC signaling and a WSS control sideband; the agent work runs as normal session turns. It uses a provider-internal Codex path and desktop-identifying headers, so service compatibility/policy may change. Linux omits the platform attestation implemented for macOS ARM; acceptance was not checked. Credential availability was deliberately not inspected. This is not the generic OpenAI API-key WebRTC flow below. |
| Dictation | RPC requires `stt.enabled`, uses `modelRoles.dictation` and `stt.language`, emits full accumulated previews and a final `dictation_end` keyed by a unique capture ID, and never submits. Stop may race start and timeout does not cancel the server operation; correlate and insert the final result only once into its originating draft. Default documented local model is Parakeet (~680 MB); model acquisition/cold start and CPU use need measurement. The exact capture plumbing beyond the RPC contract was not inspected. |

### Concrete live integration

The background service owns a voice session and exposes a dedicated narrow voice socket; web and native handlers use its client rather than each owning voice state. A separate isolated OMP live bridge binds one call generation to the existing authoritative supervisor through a narrow handoff, without attaching a second writer to the supervisor session, copying root credentials, or running a second supervisor. Normal talk remains conversation; genuine work can be handed off to the supervisor, which decides its own response and delegation. This is not an instruction to make a task for each transcript frame.

The user selects a session and supervisor root and may explicitly bind project/Space scope. Selection is frozen for the call rather than following the currently selected Workbench Space. Reuse the existing operator Inbox handoff resolver and its trust model, preserve every supplied scope field, and report canonical resolution failures without silently switching to General. Generation, session and root fences reject stale events and controls. After restart, end or explicitly recover in-flight calls; never replay an uncertain handoff.

After a user gesture and permission, the device creates the WebRTC peer, audio track and data channel and passes an SDP offer through the bounded voice interface. OMP returns an answer and emits sequenced phase, transcript, handoff and terminal events. Transcript frames are cumulative text per generation, role and turn, replacing earlier partial text through the final frame; they are not supervisor delivery receipts. The actual microphone track is muted along with bridge state. Stop, setup failure, view teardown or peer loss must stop local media and end the bridge, not cancel work already handed to the supervisor. A receipt records its own reported stage, not proof of model consumption or acceptance; preserve interrupted, disconnected and unknown outcomes.

Microphone audio travels between the device peer and OpenAI for live processing; OMP signaling and control stay host-side. Provider usage and retention policies apply, so audio must not be described as local-only. Test ICE/NAT reachability on the real tailnet/mobile network; Tailscale HTTPS does not imply that it relays WebRTC media or that UDP is available.

## Cockpit integration boundary

The Voice screen is separate from Inbox and Workbench. Inbox image and managed-browser frame channels are not bidirectional audio APIs, and managed-browser audio capability must not be flipped as a shortcut. The background owner has the sole voice state; its dedicated socket is not the lifecycle control socket or a broad proxy. The owner enforces same-UID peer checks, bounded frames and waits, and call/session generations. Same UID is a local trust boundary, not remote authentication, and peer UID alone does not authenticate an origin claim.

Remote authorization relies on the existing owner-only Tailscale HTTPS/identity gateway and its existing Host and Origin protections; a local socket's UID check is not a replacement. Native and web clients have distinct transport boundaries. These are intended contracts and source guidance, not a live gateway or packaged-native test receipt.

## Browser and native device constraints

Browser capture must happen on the user's device, not just on the Cockpit host. `getUserMedia({audio:true})` requires a secure context (normally HTTPS or localhost) and explicit permission. An unanswered permission prompt can remain pending; denied permission, missing hardware, a blocked permissions policy and an insecure origin need actionable UX where detectable. The native app uses the same browser Voice implementation in an isolated webview. [MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)

Linux WebKitGTK does not expose the requesting frame in its public media-permission callback, so a webview-wide microphone grant cannot distinguish a top-level request from an embedded frame. The dedicated Voice view must therefore prevent untrusted content, navigation and embedded frames; the main webview continues to deny media requests. On Apple platforms, native usage descriptions and, for sandboxed macOS, audio-input entitlements apply; packaged macOS behavior remains unverified. [WebKitGTK](https://webkitgtk.org/reference/webkit2gtk/stable/class.UserMediaPermissionRequest.html), [Apple](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSMicrophoneUsageDescription)

## General transport alternatives

- **WebRTC** is a proven browser bidirectional voice transport with echo cancellation and low-latency media delivery; Opus and G.711 are mandatory to implement, not necessarily the negotiated codec. A direct provider connection can use a short-lived credential minted by a trusted backend; this exposes neither the long-lived key nor the host audio device, but does send audio to the provider and is a different integration from automatically reusing OMP's current session. [RFC 7874](https://datatracker.ietf.org/doc/rfc7874/), [OpenAI WebRTC guide](https://developers.openai.com/api/docs/guides/voice-webrtc?api=realtime)
- **WebSocket PCM streaming** gives a host-side bridge control over the OMP/session boundary and keeps long-lived keys server-side; it requires explicit sample format/rate conversion, buffering, flow control, interruption and playback handling. Browser WebSockets use ordered reliable transport, so congestion can add delay. It must not be confused with browser WebRTC or the existing JSON/image streams.
- **Dictation is separate:** push-to-talk, upload a completed recording, and insert editable text is much simpler than full-duplex live talk, at the cost of waiting for utterance completion. Streaming partial transcription offers lower perceived latency but needs turn identification and finalization. Browser `SpeechRecognition` is not a dependable universal fallback and some implementations send audio to their own service. [MDN](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition), [OpenAI transcription](https://developers.openai.com/api/docs/guides/realtime-transcription)

`MediaRecorder` format support must be feature-detected, and its timeslices are not exact; chunks need not each be playable standalone. A browser WebM/Opus recording cannot simply be assumed to be raw PCM or compatible with every STT endpoint. [MediaRecorder](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/dataavailable_event), [format detection](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static)

Latency comprises capture buffering, network, end-of-turn detection, inference and playback; no end-to-end number has been measured. Provider, model, duration and output audio affect cost. Avoid logging or retaining raw audio by default; disclose processing and provider retention. OpenAI's [data controls](https://developers.openai.com/api/docs/guides/your-data) and [pricing](https://platform.openai.com/pricing) are provider-specific and change over time, not guarantees for OMP or other providers.

## Intended UX and acceptance experiments

Start live talk by explicit gesture. Show permission pending, active microphone, mute, stop, connecting, interrupted/disconnected and provider errors; do not silently reacquire audio or redirect speech to a newly selected conversation. Partial transcript text is replaced by the current complete text for its turn, and a final frame finalizes that turn. The live transcript is not an editable Inbox draft or proof of supervisor consumption. Preserve the reported handoff stage and any unknown outcome, rather than claiming success. Stop local tracks promptly on stop, view teardown, permission loss and failed setup. Interrupting or stopping a voice call must not cancel work already handed to the supervisor.

Native microphone and playback ownership must remain outside the webview, with trusted same-window controls and no blanket WebKit media grant. An isolated Linux synthetic-audio smoke exercised the native peer and controls; macOS, physical devices, packaging and the final candidate's native supervised handoff remain unverified. Embedded script-capable widget and diagram frames remain denied WebKit media access.

Verify in disposable fixtures with synthetic prerecorded audio and authorized test credentials, not the user's live sessions: assert both audio directions, exact selected session/root/binding using canonical Inbox semantics, ordinary conversation versus genuine handoff, bounded buffering, interruption and cancellation, denial/no device, delayed permission, duplicate or stale events, disconnect/reconnect, stop/teardown and receipt semantics. Include negative owner, cross-origin, opaque-frame and unauthorized stream tests, logs/retention inspection, a packaged Linux native run, remote HTTPS desktop browser and physical mobile Safari/Chrome tests including screen lock and backgrounding. Measure p50/p95 utterance-to-first-audio and final transcription under representative network conditions before claiming a latency result.
