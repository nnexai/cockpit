# Supervisor surface inventory

This is the current UI/source map and review inventory, not a record of checks run by this documentation update. [DECISIONS](../DECISIONS.md) owns authority rules; [CODE_GUIDE](../CODE_GUIDE.md) maps request flows. Historical observations remain in the [verification log](verification-log.md) and [decision archive](../archive/decisions-log.md).

## Product surfaces

Inbox is a separate switchable work-oriented screen; Workbench retains its Space/worktree hierarchy, real terminals and existing controls. A compact global bar stays visible on both screens, with flat Workbench and Inbox buttons and an accent edge marking the current view. Inbox collects human questions, requested results and other work across owners. Its badge counts threads needing the user plus relevant unmanaged agents; a preview appears in Workbench when space permits. A liaison's real terminal remains its full conversation; its compact read-only rail and optional Board/Graph Overview retain task history. Human answers can be sent through Inbox to the exact current question or given in the liaison conversation.

Batch completion leaves the session's personal liaison Active for later work across projects; worker `run done` and source cleanup do not retire it. Root completion is conversational, not another operational button.

**Ask an agent…** (Ctrl+Shift+A or Commands) is a separate quick-question surface, not supervisor startup or task delegation. It starts the agent in a new tab of the selected Space with the question as its startup argument, switches to that tab and creates no orchestration registration.

### Current UI contract and source map

- **Inbox and routing:** [`Inbox.tsx`](../src/app/inbox/Inbox.tsx) presents work threads and their details, with explicit actions and read state; the shared router aggregates handoffs without owning every root's tasks. Explicit bindings remain attached to the work rather than following selected Workbench Space. Opening a thread or navigating to its exact supervisor pane does not mark it read or resolve its question; Acknowledge explicitly marks the displayed result read, without answering a question, accepting work or notifying its owner. Follow-up is separate. The Acknowledging label appears only while that exact thread and result are being marked read, not during a follow-up or on another result; actions remain serialized. Drafts and the Workbench survive screen/Space changes.
- **Inbox presentation:** The attention queue brings questions, results and relevant direct agents together, with other work and agents available separately; a row shows a draft badge (for example “Draft ×2 · 1 img”) while the thread holds unsent text or follow-up images. The selected thread is one reading column: a timeline of requests, owner updates, questions, answers, live views and results in durable insertion order, with the reply dock docked beneath it. An open question appears once at its recorded point when retained; open questions outside the bounded timeline appear separately before the retained entries. Answers remain at their recorded points, and question references require matching identity. A thread opens scrolled to the first open card, or to the latest entry when nothing is open. An unread result's Follow up and Acknowledge actions live in that result's card. Work cards show linked task checks, commits, decisions and visual or document artifacts; diagnostics retain delivery and copyable identifiers. Images and artifacts open in viewers, with HTML isolated in a sandbox. Report text supports Markdown; raw HTML and Markdown images are not rendered. New work keeps its owner, request and optional context together. At or above an 880 px detail width Work is a column beside the thread; below it, Thread and Work are tabs, and narrow screens switch between queue and detail. A short phone viewport (on-screen keyboard) hides thread facts, tabs, the quote and hints.
- **Thread titles and artifacts:** A thread uses the owner's authored card title, otherwise its earliest linked task title, otherwise the request's first line shortened at a word boundary. Artifact viewers read only paths recorded as a linked run's non-code artifacts or named by absolute path in its Result summary: PNG/JPEG/WebP (content-checked), HTML and Markdown, bounded in size and opened without following symlinks; other files are listed for copying.
- **HTML artifact previews:** Opening an HTML artifact runs its scripts in an opaque-origin, script-only sandbox, without a Cockpit bridge. The initial document's content security policy limits native/custom schemes, nested frames, workers, form submission and base URL overrides; a navigation can replace that policy, but the iframe sandbox remains. Inline content and ordinary HTTP(S) resources and network connections are permitted; viewing an artifact can therefore contact external or local network services and disclose information the artifact contains. Native endpoints rely on their own authorization. Scripts are not isolated from CPU or memory exhaustion. Close the viewer to stop the preview; reopening starts a new document. Artifact read authorization remains unchanged.
- Thread headers, the timeline and composer use an aligned reading measure where space permits; compact rows and wrapped detail facts support narrow screens. Image-sharing and metadata disclosures appear with attached images, including on touch devices.
- **Inbox diagnostics:** Worker facts retain their source run and appear in their original order as individually expandable, task-style worker-reported evidence. A fact matching a linked task's result and run uses that task's title and is labeled a worker claim; unmatched facts use a first-line preview and remain available without assuming their type. Each disclosure provides the full selectable run ID and copy control and complete recorded Markdown. Identical facts from different runs remain distinct. Markdown HTML and images are inert; long code blocks and tables can be scrolled with the keyboard. Diagnostics and their ID copy controls remain available under Work.
- **Worker interim work and declared waits:** A linked task's interim deliverables appear as worker events with their own unread identity, not as supervisor Results or acceptance. Worker-declared waiting uses the current working attempt's recorded reason, never terminal idleness; an unresolved question takes priority without erasing the independent wait. Explicit worker resume ends the wait and states that work resumed, not that a particular delivery was consumed; ordinary progress and interim events do not clear it. Replaced attempts' events remain history and cannot set the current wait.
- **Inbox availability:** Initial loading uses a status and skeleton rows. If loading fails, the Inbox reports automatic retry; on a refresh failure it retains the last loaded items. Unavailable live observation pauses replies rather than implying that agents are ready.
- **Question and draft interaction:** The dock's `Reply to` radio group names exactly what Enter will send: `Answer` (`Answer Q1`, `Answer Q2` when several are open) for one exact `(run_id, question_message_id)`, or `Follow up`. A single open question is preselected; with several, nothing is chosen and the field stays disabled until the user picks a target. Selecting never sends, resolves or marks anything read; arrow keys move and select within the group without entering the field, and pointer selection focuses the field on non-touch devices only. A quote under the group repeats the question being answered (`Show question` scrolls to and focuses its card) or states that a follow-up is not an answer. Each open question has its own draft, separate from the thread's follow-up draft; switching targets never merges, moves or deletes text. A choice button selects its question and fills the draft only when it is empty; over different text it asks `Replace`, `Add below` or `Keep mine` (Escape keeps the typed text). A confirmed answer clears that question's selection and returns to follow-up so later follow-ups are not mistaken for answers. A question that changed or was answered elsewhere never receives the old text: with exactly one open question from the same owner the draft moves there with a visible “carried over” note and the selection returns to follow-up; otherwise the draft stays visible as an unsent answer that can be reused as a follow-up or discarded. Enter sends from the composer, while Shift+Enter inserts a newline and IME composition does not send; Escape cancels a pending choice replacement, otherwise moves focus to the question card (or the timeline for follow-ups) without touching the draft. Failed or uncertain delivery retains the draft, makes the field read-only and offers Retry original request, which preserves its identity. While live sessions are unavailable, replies are paused, typing is still allowed and drafts are kept.
- **Follow-up recipient:** When a linked task has a present Working or Reported worker, `Send to` offers Supervisor (the default) or that task's worker. Selecting a worker hides the separate About selector because the task is implied; switching recipients neither sends nor clears the thread's follow-up draft. Sending rechecks the current task revision and worker; if the worker is no longer available, the draft is kept for sending to the supervisor instead. Worker-targeted messages, including images, are recorded as task directives and appear in the timeline as `To worker · {task title}`.
- **Stalled supervisor:** A muted notice above the queue shows a supervisor idle with open work and the time since the stall, with Open supervisor navigation. It has no dismiss state; it is a non-waking observation, not a new thread.
- **Inbox images:** New requests and managed follow-ups accept PNG and JPEG images by file selection, clipboard paste or file drop where supported. The composer shows preparation and failure states and allows removal before sending. Images are stored separately from messages with bounded size and storage, and delivered through scoped Inbox access; linked workers can use `cockpit-cli inbox images` to locate authorized images for their harness. Images may retain metadata such as EXIF location. Markdown image URLs remain inert; Cockpit does not fetch them. Images share the local account's filesystem permissions rather than providing OS isolation between agents. Abandoned uploads count toward the bounded store and are not automatically deleted.
- **Inbox answers and images:** Answers are text only; images attach to follow-ups and new work. In answer mode the dock says so, and links to Follow up (noting how many images the follow-up draft holds, which are not included in the answer).
- **Inbox narrow navigation:** On a phone-width Inbox, Back and Escape (when focus is not in a field, dialog or choice prompt) return from a thread to the queue and focus the row it was opened from; the thread's tabs switch between Thread and Work with the arrow keys.
- **Inbox detail views:** Thread, direct-agent and New work views share one header: Back (narrow widths only), a state icon, the title over its facts, then actions; Open session is disabled while live sessions are unavailable. Queue rows lead with the state word and age (`Question`, `2 questions`, `Result · Succeeded` or `Failed`, `Working`, `Handled`), then the title and preview, and Up/Down move focus between rows without opening them. An answered question stays one entry: its text is clamped to three lines with Show more, followed by `You answered` and a delivery receipt such as `Stored · waiting to be picked up`, which never claims a model read it; a confirmed answer is also announced politely with the number of questions still open. A question that received a carried-over draft says `Updated by <owner>`. Days read Today or Yesterday, timeline thumbnails are 84×54 and open the viewer, and an empty Work panel says so. While the inbox is loading or unreachable, New work shows a status instead of a composer, and work that left the inbox while selected reads `Work no longer available`. Inbox metadata text is never smaller than 12 px.
- **Unmanaged completion attention:** Opening an agent row selects its detail and acknowledges the completion captured at selection when the fresh direct target matches the live agent identity. A later completion remains unseen; the selected detail remains open even when the agent moves out of the attention queue. Open session retains its separate behavior: it acknowledges the completion shown at activation only after the exact terminal focus is accepted and confirmed, provided the session and agent identity are still current. This is independent of managed-thread Acknowledge and does not change sidebar acknowledgement.
- **Direct-agent context:** Unmanaged direct-agent rows and details can show the same context as the Agents sidebar. Labels distinguish **Session title** from **Agent title**, and **Current activity** from **Session recap · OMP session**. OMP context is joined only when the live pane, terminal, agent and native session identity agree with the direct target; otherwise Cockpit can fall back to a meaningful Herdr agent title or the existing row and status. Managed threads keep their authored task and thread context rather than acquiring context merely from a matching pane.
- **Source and freshness:** OMP context is available only when Herdr identifies an OMP path-backed session and Cockpit can read its matching local session data. The title comes from the session journal; current activity comes from an outstanding structured tool invocation, not an inferred narrative. For idle or done agents, a recap comes from OMP's local session history only when its timestamp is strictly later than the latest complete final turn visible in the bounded journal tail. This timestamp comparison is conservative, not a turn-ID guarantee; missing, ambiguous, inaccessible or out-of-window data can leave context absent. Other agents retain the existing Herdr title and status fallback.
- **Title symbols:** Workbench tab and pane titles, sidebar labels, the quick switcher, and direct-agent Inbox context can display the Material Design range of Nerd Font private-use symbols without a locally installed Nerd Font. Other icon sets are not bundled. Ordinary text keeps the UI font, and title strings and accessibility labels are not rewritten. Terminal font configuration is separate. The bundled font is a modified subset (`U+F0001–U+F1AF0`) of [Symbols Nerd Font v3.5.1](https://github.com/ryanoasis/nerd-fonts/tree/v3.5.1/patched-fonts/NerdFontsSymbolsOnly), copyright © 2014 Ryan L McIntyre ([MIT license](../public/fonts/SymbolsNerdFont-LICENSE.txt)); its Material Design icons are by [Pictogrammers](https://github.com/Templarian/MaterialDesign-Font) and distributed under [Apache License 2.0](../public/fonts/MaterialDesign-APACHE-2.0.txt), with the [upstream notice](../public/fonts/MaterialDesign-NOTICE.txt). The subset was made with `pyftsubset --unicodes=U+F0001-F1AF0`; see the upstream [range mapping](https://github.com/ryanoasis/nerd-fonts/blob/v3.5.1/font-patcher).
- **Delivery and authority:** Handoffs and replies preserve recorded receipts separately from model response. A root may update its own threads, not another root's; replacement bindings and exact question identity are fenced. Managed follow-up checks the current owner, task revision and attempt. Explicit direct sends to unmanaged agents use the expected opaque target and do not adopt them. A successful direct send is shown as submitted to the terminal, not confirmed read; the header continues to show live status. The four definitive pre-dispatch busy/not-ready outcomes show Not sent, retain the draft and require reselecting the agent. Stale identity likewise retains the draft for review and reselection. Other failures leave delivery uncertain: inspect the session before sending again; there is no automatic replay. Outcomes stay scoped to the selected target.
- **Direct-send readiness:** The current agent status must be idle or done; working is not ready. Exact target identity checks remain in force.
- **Mobile input and viewport:** On a coarse pointer, a single-finger terminal drag scrolls through Herdr without focusing or sending local arrow input; a tap focuses the terminal. Automatic attachment, frame and popup focus do not summon the keyboard. Mouse, pen and wheel behavior remain unchanged, and pinch zoom remains available. The shell tracks the visible viewport for keyboard resizing; zoom does not reset the pan or relayout it.

- **Conversation and startup:** [`useLiaison.ts`](../src/app/supervisor/useLiaison.ts) looks up the session's eligible liaison, reuses/resumes it and navigates to its exact real pane. A new liaison works in `<state>/supervisors/<run_id>` and its terminal moves into its own Supervisor Space; a start target is optional staging. [`useLiaisonNavigation.ts`](../src/app/shell/useLiaisonNavigation.ts) toggles between liaison and origin pane with Ctrl+Shift+L (Cmd+Shift+L on macOS); Commands offers Start/Resume supervisor, Go to liaison or Back to the origin Space.
- **Supervisor recovery** offers a retry and, when the backend can isolate a fresh conversation and no launch remains in flight, **Start new conversation (tasks kept)**. Currently that fresh path supports the default OMP adapter without resume/session-directory arguments; other harnesses and unsettled launches do not yet have this path. Starting fresh preserves the durable root and task history, fences the previous root credential and leaves the old terminal untouched. The separate stopped-confirmation path still checks the old terminal before resuming the same conversation. An unconfirmed mutation retries the same operation instead of starting another conversation.
- If an effect-free supervisor launch is refused because its saved checkout identity changed, Cockpit shows the refusal instead of indefinite resuming. Selecting the retained Space permits **Resume in this folder**; locked admission rechecks the root, current folder, and absence of conflicting launch effects before reusing the reservation. Other Spaces cannot rebind it.
- After a reboot or Herdr restart, Resume relaunches the supervisor in its retained Space whenever that Space still uniquely shows the saved folder; no explicit re-selection is needed. Checkout identity compares canonical path and inode only, because Btrfs subvolumes and macOS volumes may report a different device number for the same directory after a reboot.
- A supervisor replacement whose launch requires review is shown as blocked rather than indefinitely resuming. Cockpit preserves the recorded attachment, credentials and tasks; it does not infer that the old process stopped or launch a replacement. A known effect-free refusal retains its existing retry or checkout-reselection path.
- An unregistered direct launch with an unknown outcome offers Resume rather than remaining indefinitely Starting or Resuming. Automatic exit proof requires a freshly observed drained launch scope; uncertain or populated scopes remain blocked. For an eligible root without recorded process identity, the operator may instead confirm that the supervisor and all its processes have stopped and its terminal is closed; Cockpit checks the terminal is absent twice but cannot verify the processes.
- A fresh supervisor retry with a retained checkout keeps its fresh-conversation intent until a conversation registers. If an older version lost that intent before an effect-free launch, an operator retry reuses the reserved attachment only when the durable prior fresh-conversation receipt and namespace match; uncertain launch evidence stays blocked. Adopted roots do not use this retry path.
- A retained Space is reused automatically only when its server and checkout are proven. If that identity is unproven, the operator can select the retained Space and resume there; Cockpit pins the current Herdr peer and local boot, rechecks the Space and terminal, and fences the waiting launch to the saved checkout before execution.
- Successful supervisor diagnostic reports can omit source output; decoding them must not take the session offline. Successful worker Results still require their recorded output.
- A liaison focus request superseded by a different selection releases its pending acknowledgement, so a later navigation can retry; a reissued focus for the same pane still waits for confirmation.
- Recognized recovery refusals use [`plainErrors.ts`](../src/app/shell/plainErrors.ts) for a short explanation and next step, with the original code and host message available as secondary detail. Unknown messages remain unchanged.
- **Quiet liaison labels:** [`useLiaison.ts`](../src/app/supervisor/useLiaison.ts) supplies exact root/tab/pane identity. [`WorkbenchContent.tsx`](../src/app/shell/WorkbenchContent.tsx) passes `liaisonTab` to [`TabStrip.tsx`](../src/app/shell/TabStrip.tsx); **Supervisor** appears only for matching recorded tab ID and raw launch-tag label. [`WorkbenchCanvas.tsx`](../src/app/shell/WorkbenchCanvas.tsx) passes **Liaison** through [`LeafHost.tsx`](../src/app/layout/LeafHost.tsx) only for the exact root pane/raw launch-tag title. Custom labels stay unchanged; aliases never mutate IDs, durable tags, focus/drag/rename payloads or membership proof.
- **Compact rail and task history:** [`SupervisorTasks.tsx`](../src/app/supervisor/SupervisorTasks.tsx) attaches the rail to the actual liaison [`TerminalLeaf`](../src/app/layout/TerminalLeaf.tsx) through [`LeafHost`](../src/app/layout/LeafHost.tsx). Tasks group by project with General last; group counts show `N open · M done`, and completed rows remain inside their projects. [`TaskHistoryDetail.tsx`](../src/app/supervisor/TaskHistoryDetail.tsx) opens in place; Back/Escape restores row focus. No tasks hides the rail. Task project comes from the latest attempt or schedule target, or is General when absent; tasks remain distinct from replaceable attempts.
- **Recorded evidence, not an event log:** [`taskHistory.ts`](../src/app/supervisor/taskHistory.ts) derives only the selected task's root-scoped attempts, reports/results, answered questions, integration and latest resource outcomes from the existing snapshot. Older attempts fold under their reason. Task outcome and resource disposition remain separate. Times come from recorded events, not generic run/cleanup update fields; task creation and acceptance times are not invented. Latest-only recovery is labelled as a last update. Lost live observation keeps recorded history visible and marks unresolved resource presence unobserved; durable removal evidence remains recorded.
- **Fullscreen Overview and task detail:** [`SupervisorView.tsx`](../src/app/supervisor/SupervisorView.tsx) keeps Board and Graph visible while a selected task's [`TaskHistoryDetail.tsx`](../src/app/supervisor/TaskHistoryDetail.tsx) appears in an adjacent inspector. It uses the same [`taskHistory.ts`](../src/app/supervisor/taskHistory.ts) projection as the rail and the full liaison snapshot/root/freshness from [`WorkbenchContent.tsx`](../src/app/shell/WorkbenchContent.tsx). Narrow views stack detail below the overview, not in another fullscreen view. Close/Escape restores the originating card, node or outline row and retained overview scroll; a subsequent Escape or Conversation returns to the liaison. The header and Board/Graph switch remain available with detail open. Completed board tasks beyond the initial twelve remain reachable through local disclosure. A vanished task closes detail without taking external focus; changing store/root resets selection. [`useWorkarea.ts`](../src/app/shell/useWorkarea.ts) owns the `overview` workarea, not task-editing or startup-modal tokens. Inspecting details never submits work or focuses a worker.
- **Why waiting:** Task detail reads the task's `waiting` projection: recorded cause, optional event time and detail/code, related task references, and whether the next action is automatic. Its progress rail shows Ready → Working → Review → Accepted, adding Integrated only for a recorded integration. A checked task alone does not mark acceptance as recorded. Accepted Code with pending integration says "Integration not recorded"; accepted NonCode with a matching NotApplicable record says "Non-code result · no Git integration needed". Missing or mismatched output implies neither. Recorded integration is described as "Integrated into", including patch-equivalent and adapted integration, not necessarily a merge. Overview's task attention uses the same cause for queued tasks instead of "reason unknown", after any named prerequisite. Absence of recorded evidence is not an inferred cause or age. CLI `task show --json` and `task list --json` expose the same task view; human `task list` adds a `waiting:` line with any hold code; `run list --json` exposes it in the selected board, and `run show --json` reports the associated task's current waiting state, including for older attempts.
- **Task attention in Overview:** A compact read-only list above Board and Graph uses the snapshot's attention for uniquely identified tasks and their current root-scoped runs. It covers all projects regardless of the Board project filter, as its heading indicates. It distinguishes unresolved input, reported success or failure (not task acceptance), and uncertain or blocked runtime observations; a stored work brief is not evidence of delivery or understanding. Healthy observed work alone does not create a row; on actionable rows, current-run observations carry their observation time, with stale or unavailable runtime observations labelled. A working run without an eligible current observation says its live worker state is unknown. Scheduled work without a known cause says dispatch is waiting and the reason is unknown; known prerequisite blockers are named. Each row opens the same task history and Close/Escape restores focus to the originating row. This list adds no operational authority.
- **Board and prerequisite graph:** Board shows five task columns and project filter chips when more than one project exists. Graph hides these filters. [`SupervisorGraph.tsx`](../src/app/supervisor/SupervisorGraph.tsx), [`dependencies.ts`](../src/app/supervisor/dependencies.ts) and [`dependencyLayout.ts`](../src/app/supervisor/dependencyLayout.ts) render the canonical prerequisite DAG, not a run/agent hierarchy. Canonical dependencies and stable tasks do not disappear when an execution attempt is replaced.
- **Actual dependency inputs:** Canonical checked prerequisites and accepted status are not a guarantee that a same-repository Code output is in the next checkout. Scheduling freezes/validates actual predecessor commits or holds work queued with a concrete liaison cause. NonCode output references remain accessible and preserved. Graph/board remain observational; no per-step approval or operational retry UI is added.
- **Quiet human-wait hint:** [`useLiaison.ts`](../src/app/supervisor/useLiaison.ts) checks the nonclosed root's question (`run_id === root.run_id`) for `QuestionStatus.receipt.status === "unresolved"`, not historical `last_report`. Core `current_question(messages)` preserves questions across Progress. Exact actual-human `run answer` capture clears unresolved state while keeping NeedsInput history; stale/replayed answers cannot clear newer questions. The hint appears in rail/Overview, [`TabStrip`](../src/app/shell/TabStrip.tsx) and [`WorkbenchContent`](../src/app/shell/WorkbenchContent.tsx)'s polite live region. Worker questions and cleanup/recovery remain liaison-owned.
- **No dead operational dashboard:** Global Activity, Diagnostics, archive, worker Answer/Retry buttons, task/step editors and decision forms remain removed. The Overview's task-local attention list and shared history are observational, not another control surface. Durable CLI coordination and ordinary project teardown/recovery remain available. `run list --json` also keeps the derived `attention`, `roots[].needs_you` and `unmanaged_agents` fields as public CLI output.
- **Agent and local operator authority:** Private attempt credentials and generations fence autonomous coordination; conversation metadata remains optional and validated when supplied. Explicit local CLI `--operator` management uses named targets without requiring a private job capability or repairing stale attachment metadata. Terminal effects and automatic cleanup retain exact physical target checks. Manual linked-worktree removal uses the local user's fresh review and confirmation, not historical setup ownership. Atomic isolated replacement preserves old dirty/unmerged work and claims.
- **Quiet scoped observation:** [`useSupervisor.ts`](../src/app/supervisor/useSupervisor.ts) observes the selected session/root and task token. Directory notifications cover cross-process commits and external Markdown edits, including atomic replacement; unchanged wait deadlines renew without refreshing full snapshots. CLI inbox pending waits read durable metadata, not bodies, task boards or live Herdr. Watch/backend failures retry on the next wait. Cleanup watches Git common-directory refs and each relevant root checkout's `HEAD`, including linked-worktree Git directories; objects/index/read/lock churn does not wake it. Retired resources remove watches, and directory replacement/backend errors rebuild registration.
- **Output publication wakes:** The same watcher covers the attempts root and immediate UUID output directories nonrecursively. Output-entry create/remove/rename wakes empty-only cleanup after durable publication/move; reads, content changes and nested-tree activity are ignored. No timer or UI retry is required, and watch registration grants no deletion authority.
- **Launch and delivery honesty:** Literal initial prompts and optional per-launch OMP hooks remove required skill/identity/ACK model turns. Credential-scoped `inbox next` captures messages internally; capture is not model processing or an Answer. Inbox Delivery shows an acknowledged message as "captured, processing not confirmed". Launch acknowledgement, observed physical readiness, credential activation and first model response are separate observations. Desired launch/communication targets are not measured acceptance here.
- **Inputs needing review:** A Reported task's Overview can flag inputs recorded after its current Result or still Stored, and task history retains their recorded stage and available body for Reported and Accepted attempts. The `unreflected_inputs` projection covers nonstale instructions, user directives, answers and cancel requests appended after the Result or still Stored without a recorded pickup; absence of Result evidence yields no inference. A later input cannot be reflected in that earlier Result, but its stage does not prove whether a model saw or processed it. This is observational, not an acceptance or retirement gate; use explicit `task continue` for further work, not automatic replay.
- **Cleanup and recovery:** Durable, pane, ref and target-HEAD events trigger reevaluation. Transient foreground-process retirement holds also receive targeted five-second retries without global idle polling. Accepted retired worker scope stop does not require target integration. Clean owned accepted Git resources contained by ancestry or patch equivalence in the project's primary checkout can retire non-force without an IntegrationRecord; integration status/check evidence stays unchanged. Dirty/unmerged output and unproven consumers remain protected. Manual Space removal separately offers actual removal, including an explicit reviewed discard confirmation, rather than a review-only dead end.
- **Borrowed-checkout holds still reach the liaison:** A scope hold with no eligible owned filesystem/Space row sends an existing Dispatcher Observation only for the exact current run/epoch and pending owned claim/holder with a nonclosed root. Durable run/epoch/cause dedup survives capture/restart; a different concrete cause may produce one new notice. No pending claim means no notice. This meaningful boundary is not quiet Progress, fabricated ownership/resource data or a new UI; drain/release/foreign-consumer gates are unchanged.
- **Pane-close capability hold:** Explicitly borrowed primary-Git workers remain Kept with `primary_checkout_space` / `terminal_primary_checkout_space` when the Cockpit adapter returns `foreign_space_group_close_risk` before submission. This is not a Herdr refusal or an unknown close: the existing intent settles as Refused without replay. Scheduled Git paths can borrow a clean lone-writer checkout or use isolated worktrees; linked/non-Git permits only exact pane close, never workspace close, under normal proof gates. No new operational controls or permission to affect foreign grouped Spaces are introduced.
- **Fresh absence proof:** Owned Space absence matches exact endpoint/session/placement, then genuine recorded/fresh legacy boot or proved NativeProcessIdentity Some pair; conflicting both-present boot/peer evidence refuses even if the other matches. Same-FD own-UID PID/start/kernel/still-running proof is immutable in retirement/location. Foreign Git census independently requires fresh complete peer, not historical run identity. None/opaque/missing never proves absence; no hash/backfill/global endpoint change or host-ID startup gate is introduced.
- **Contained same-boot cleanup:** Accepted-worker stop needs current exact accepted/retired output proof and no Held/Queued holder; Code needs the clean accepted HEAD, not target integration. NonCode retains its exact Result/source/NotApplicable/artifact/check attestations. Separate committed WorkerReplace authority may retire the exact old idle Superseded pane and stop only its verified old scope, never old files. Foreign cwd consumers block later claim release/deletion proof, not isolated scope stop. Superseded data remains Kept after release; roots/cancelled/arbitrary scopes never stop. Escaped writers require separate consumer proof.
- **Directory replacement/output preservation:** Live/unknown Directory writers can be replaced in private no-copy attempt directories while original project/context/source and old resources/claims remain unchanged. `COCKPIT_SOURCE_PATH` is read-only by instruction, not a sandbox. Accepted/NotApplicable output is not deletion authority: only exact accepted retired drained EMPTY owned attempts can retire. Nonempty deliverables stay `outputs_kept` until durable publication/move; cancelled/superseded/failed attempts remain preserved. No new operational UI.
